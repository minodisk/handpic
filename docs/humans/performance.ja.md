## Leica M11-P DNG（Apple Silicon Mac、n=32）

リリースビルドで、32 個の異なる実際の M11-P の DNG（60.8MB から 78.0MB、平均 72.0MB）を、ページキャッシュが温まった状態（直前にファイルを読み込み済み）で計測しました。各 DNG は 2112x1408 のプレビューと 9504x6320 の等倍 JPEG を埋め込んでいます。M11-P は `FocusLocation` を記録しないため、512px の切り出しはアプリのフォールバックと同じく画像の中央（約 3160 行目）で行います。

`handpic-cli bench`（2 回実行、中央値）:

| 処理 | 目標 | 実測（中央値） |
|------|--------|-------------------|
| 2112x1408 のプレビューのデコード | 10ms | 7.5-8.0ms（α7 V の 1616x1080: 4.4ms） |
| 9504x6320 の等倍 JPEG の全体デコード | 300ms | 105ms（p95 125-130ms） |
| 中央での 512px 部分デコード | 50ms | 16.4-16.5ms（p95 約 20ms、最大 22.7ms） |

中央の切り出しだけなら 50ms の予算に十分収まります。これは CLI でのデコードだけの数字で、キー入力から画素が表示されるまでの時間ではありません。

このフォルダーに対する `handpic-cli scan`:

| スレッド数 | 合計 | スループット | ワーカー上の 1 ファイルあたり（平均 / p95） |
|---------|-------|------------|-----------------------------------|
| 1 | 0.39s | 83 files/s | 12.1ms / 14.1ms |
| 12 | 0.05s | 596 files/s | 17.3ms / 24.2ms |

サムネイル（当時は 528x352）: 1 ファイルあたり平均 30,231 バイト（32 ファイルで 967,419 バイト）で、α7 V の約 19KB に対して大きくなっていました。現在は 404x270 です（後述の「サムネイルの大きさ（Windows 11）」を参照）。

| | NEF | CR3 | ORF |

## Fujifilm RAF（raw.pixls.us のサンプル、Windows）

[カメラが記録する情報](./cameras.ja.md)に載せている 22 機種の Fujifilm のカメラについて、raw.pixls.us のサンプル 46 個（カメラごとに圧縮と非圧縮のサンプル 1 つずつと、クロップモードのサンプル 2 つ）を `handpic-cli bench` / `scan` で計測しました。

| | RAF |
|---|---|
| プレビュー（= フルサイズ JPEG） | X シリーズで 4416x2944、GFX シリーズで 4000x3000、1.27-5.51MiB |
| プレビューのデコード | 48-147ms（平均 90.6ms、p95 120.7ms） |
| 先頭 1MiB 以内のメタデータ | すべてのカメラ（JPEG の Exif は約 66KB までに終わる） |
| 先頭 1MiB 以内のプレビュー | なし: プレビューも等倍表示も、開くたびに 1 回の範囲読み込み（ウォーム時 1-4ms） |
| `scan`、1 スレッド | 1 ファイルあたり平均 221.8ms、p95 290.2ms（5 files/s） |
| `scan`、24 スレッド | 36 files/s |

RAF には JPEG が 1 つしかないため、プレビューと等倍表示は同じ画像をデコードします。ほかの形式の約 1620x1080 のプレビューよりはるかに大きいため、RAF のサムネイルは、当時ほかの RAW 形式が使っていた固定の 2/8 の縮小ではなく、通常の JPEG ファイルと同じく `thumbnail_jpeg_near` で `JPEG_THUMBNAIL_LONG_EDGE` に近づけてデコードするようにしました（現在はすべての形式がそうしています。後述の「サムネイルの大きさ（Windows 11）」を参照）。サムネイルは長辺 404 px（平均 19.4KB。2/8 では 1104x736 で約 111KB）になり、サムネイルのエンコードは 1 ファイルあたり 37-107ms から 16-60ms に下がりました。それでも 1 ファイルあたりのスキャンのコストが高いのは、シャープネスのスコアが JPEG 全体をデコードし、AF 点を読まないため顔を画像全体から探すからです。この 2 つはその後スキャンの 2 回目のパスに移ったため（後述の「どのパスがどのコストを担うか」を参照）、上の `scan` の行は 1 パスだったころの記録で、現在の `handpic-cli scan` の計測結果ではありません。

現在の 2 つのパスは、2026-11-23 に Windows 11（i7-13700）で、リリースビルド、1 スレッド、ウォームな状態で、X シリーズの RAF 20 個のフォルダーと Sony ARW 20 個のフォルダーを比べて計測しました。マシンはほかのセッションの cargo のビルドと共有しており（CPU 負荷がときどき約 100%）、アイドルを待たずに計測したので、数値は目安です。

| | RAF | ARW |
|---|---|---|
| 1 回目のパス（`handpic-cli scan`）、1 ファイルあたり平均 / p95 | 89.7ms / 122.5ms | 31.2ms / 60.9ms |
| 2 回目のパス（`handpic-cli features <dir> 1` の `analysis_ms`）、平均 / p50 / p95 | 299.0 / 294.4 / 393.7ms | 140.1 / 116.5 / 227.1ms |

RAF は 20 個すべてに AF 点があったので、どれも顔を画像全体から探してはいません。計測した時点では、2 回目のパスは 4416x2944 のプレビューを 2 回フルサイズでデコードしていました。顔の手がかりのための RGB（約 74ms）と、シャープネスのスコアのためのグレースケール（約 50ms）です。`FACES_VERSION` 17 からはスコアが手がかりの RGB のデコードの BT.601 の輝度で取られるため、グレースケールのデコードはなくなりました（「どのパスがどのコストを担うか」を参照。RAF での短縮は計り直していません）。これらのプレビューを mozjpeg の DCT で縮小してデコードしても速くなりません（平均、n=20、各ファイルの 2 回のデコードのうち 2 回目）。

| 縮小率 | グレースケール | RGB |
|-------|-----------|-----|
| 8/8 | 50.5ms | 74.0ms |
| 4/8 | 64.5ms | 84.7ms |
| 3/8 | 73.1ms | 87.3ms |
| 2/8 | 78.0ms | 80.0ms |

そのため、シャープネスのスコアはフルサイズのデコードのままとし、RAF のスキャンは変更しませんでした。より小さな DNG と ARW のプレビューで縮小デコードを計測した以前の結果は、後述の「プレビュー全体の探索での DCT で縮小したデコード（Windows 11）」にあります。

## サムネイルの大きさ（Windows 11）

`scan` はすべてのファイルのサムネイルを `thumbnail_jpeg_near` で `JPEG_THUMBNAIL_LONG_EDGE`（長辺 404 px）に近づけて作ります。プレビューを、長辺が 404 px を下回らない最小の `n/8` の縮小率でデコードし、そこから 404 px までボックス平均で縮小します。2026-11-24 までは RAF 以外の RAW のプレビューを固定の 2/8 でデコードしていたため、通常の約 1620x1080 より大きいプレビューでは 404 px を大きく超えていました。プレビューの段がフルサイズ JPEG にフォールバックする SIGMA fp L では、サムネイルの画素数がほかのカメラの 10 倍を超えていました。

2026-11-23 に Windows 11（i7-13700）で、リリースビルドで変更の前後を計測しました。マシンはほかのセッションの cargo のビルドと共有しており（CPU 負荷がときどき約 100%）、アイドルを待たずに計測したので、時間は目安です。デコードは、保存したサムネイルをストリップがセルごとにデコードする時間で、5 回の最小値です。

| カメラ（プレビュー） | 変更前 | 変更後 |
|---|---|---|
| SIGMA fp L（9520x6328） | 2380x1582、141,610B、エンコード 815ms、デコード 12.80ms | 404x269、9,829B、エンコード 405ms、デコード 0.31ms |
| SIGMA fp（6000x4000、3 ファイル） | 1500x1000、73-86KB、エンコード 204-250ms、デコード 5.2-5.4ms | 404x270、11-15KB、エンコード 109-153ms、デコード 0.34-0.37ms |
| OM System / Olympus ORF E-M10 II（3200x2400、3 ファイル） | 800x600、47-74KB、デコード 2.1-4.1ms | 404x303、15-19KB、デコード 0.43-0.80ms |
| Sony ARW ILCE-1M2（1616x1080） | 404x270、約 8.8KB | 同一 |

この変更では `EXTRACTOR_VERSION` を上げていないため、変更前にインデックスした行は、ファイルが変わるかキャッシュを消去する（設定の `Cache` ページの `Clear Cache`）まで、大きいサムネイルのままです。

## ページごとのプレビュー読み込み

Apple Silicon Mac での、読み込みだけのページごとのコストです。アプリのエンドツーエンドの数字は後述の「キー入力から画素の表示まで（GPUI）」にあります。48MB の ARW 全体の読み込み（`std::fs::read` と `arw::parse`）と、メタデータと埋め込みプレビューがある先頭 1MiB に限った読み込み（`reader::read_preview`）を比べています。

| フォルダー | n | ファイル全体 | 先頭部分に限った読み込み（Handpic） |
|--------|---|---------------------|------------------------|
| 1 つの ARW への 5000 個のシンボリックリンク、ウォームなページキャッシュ | 300 | 平均 6.6ms / p95 7.7ms | 平均 0.06ms / p95 0.13ms |
| 48MB の異なるコピー 20 個、初回の読み込み | 20 | 平均 16.0ms / p95 30.0ms | 平均 5.1ms / p95 7.8ms |

両方の列は同時に計測したので、同じ条件で比べています。シンボリックリンクのフォルダーは同じファイルへの 5000 個のシンボリックリンク、コピーのフォルダーは `cp` による 20 個のコピーで、新しいプロセスがファイル名順に読み込みました。「初回の読み込み」の列がコールドである保証はありません。

大半を占めるのはファイル全体の読み込みで、先頭部分に限った読み込みはそれをなくします。

### キー入力から画素の表示まで（GPUI）

アプリのページャー（`crates/app`、当時は試作中）で、キー入力からフレームの提示まで（vsync 待ちと `Present` を含みます）を測りました。3 回の実行それぞれの p50 / p95 の中央値を ms で示します。各実行は n=20 でタイマー駆動のキー入力、2026-11-09 に計測しました。条件は Windows 11、SIMD 付き mozjpeg のリリースビルド、i7-13700、RTX 4060 Ti、5120x1440 の 59 Hz、SATA SSD、捨て実行で温めたファイルです。計測したキー送りの間の負荷は 15 % 以下でしたが、以前の Tauri アプリが開いたままで、マシン上で他の作業も動いていました。p95 は 20 サンプルの最大です。

| ケース | keypressToPixels | read | decode | frameWait | paint |
|---|---|---|---|---|---|
| ARW, 1616x1080 | 20.9 / 30.0 | 1.6 | 7.8 | 8.1 | 0.7 |
| RAF, 4416x2944 | 64.8 / 75.2 | 3.6 | 47.6 | 8.5 | 3.5 |

当初設定した移植のしきい値（17.6 ms と 62.9 ms）には届きませんでした。このしきい値は使い捨てのスパイクの n=20 の 1 回の実行（15.56 / 57.89 ms）に余裕を足したもので、同じバイナリは下の同一セッションの再計測で 19.86 / 64.59 ms となり、スパイク自身もこれを満たしません。実行ごとの数値、計測条件、どのステージが伸びたかは [`results.md`](../plans/20261109-gpui-port/results.md) にあります。

同じ日に、以前の Tauri アプリを閉じた状態で、このページャーとスパイク本体のバイナリを交互に計測し直しました（それぞれ 3 回、20 ファイルを 60 回送り）。ページャーは ARW で 20.2 ms、RAF で 65.9 ms、スパイクのバイナリは 19.9 ms と 64.6 ms でした（3 回の実行の `keypressToPixels` の p50 の中央値）。ページ処理の所要時間はページャーとスパイクで同じで、RAF に残る約 1 ms の差は、スパイクが回転させない縦位置のページでの `orient` ステージと整合しますが、切り分けてはいません。

サムネイルのストリップ、インデックス、フォルダースキャンの 1 回目のパスを加えたページャーを、それらを加える前のページャーと同じセッションで交互に計測しました（2026-11-10、それぞれ 3 回、20 ファイルを 60 回送り、インデックスは計測前に埋まった状態、3 回の実行の `keypressToPixels` の p50 / p95 の中央値）。

| ケース | ストリップあり | ストリップなし |
|---|---|---|
| ARW, 1616x1080 | 17.4 / 25.4 | 16.6 / 24.4 |
| RAF, 4416x2944 | 60.3 / 71.8 | 59.8 / 72.3 |

ストリップによる増加は p50 で ARW が 0.8 ms、RAF が 0.5 ms で、`paint` は増えていません。1 回目のパスの実行中も、スキャンが現在のファイルの周りを先に読むため、プレビューの読み込みは 1 ms 前後のままです。実行ごとの数値と計測条件は [`results.md`](../plans/_archived/20261110-gpui-strip-index/results.md) にあります。

ここでの絶対値は、同じファイルと同じマシンでの 2026-11-09 のセッションより低くなっていますが、理由はわかっていません。比べられるのは同一セッション内の差だけです。ここでの p95 は 60 サンプルのうち 57 番目で、20 サンプルの最大ではありません。

フォルダースキャンの 2 回目のパス（顔、ピント、目）の実行中も、ページ送りの遅れは計測できるほどには増えません。これは、このパスをコアの 8 分の 1 で動かし、プレビューの読み込み、デコード、描画の間は処理を止めるようにしてからの結果です（2026-11-13、同じセッションで処理済みのインデックスでのページ送りと交互に計測、それぞれ 3 回、20 ファイルを 60 回送り、3 回の実行の `keypressToPixels` の p50 / p95 の中央値）。

| ケース | 2 回目のパスの実行中 | 2 回目のパスの完了後 |
|---|---|---|
| ARW, 1616x1080 | 18.4 / 25.0 | 20.5 / 29.4 |
| RAF, 4416x2944 | 63.6 / 74.9 | 63.9 / 76.5 |

全コアで動かし、止めるのが読み込みだけだったときは、2 回目のパスで ARW は 9.4 ms、RAF は 89 ms 遅くなっていました。このパス自体は、24 論理コアで ARW 18,620 ファイルに約 5 分、RAF 5,420 ファイルに約 4 分かかるようになりました。実行ごとの数値と計測条件は [`results.md`](../plans/_archived/20261110-gpui-focus-marks/results.md) にあります。

メタ情報ペインと判定（星、フラグ、ラベル、サイドカーの書き込み、取り消し / やり直し）を加え、あわせてその間に他の計画で入った機能（等倍表示、フォーカスマークのオーバーレイ、スキャンの 2 回目のパス）も含むページャーを、それらすべてを加える前のページャーと同じ方法で比べました（2026-11-13、インデックスは計測前に埋まった状態）。

| ケース | ペインと判定あり | それ以前 |
|---|---|---|
| ARW, 1616x1080 | 22.4 / 32.0 | 21.6 / 31.6 |
| RAF, 4416x2944 | 64.0 / 78.9 | 65.5 / 76.3 |

p50 の差は ARW が +0.9 ms、RAF が -1.5 ms で、実行ごとのばらつきの範囲内です。すべての実行で増えたのは `present` だけで、その増加は 0.1 ms 程度までです。実行ごとの数値と計測条件は [`results.md`](../plans/_archived/20261110-gpui-judgments/results.md) にあります。このセッションの絶対値は 2026-11-10 のセッションより高くなっていますが、こちらも理由はわかっていません。

ストリップの絞り込みと並べ替え（`Sort ▾` と `Filter ▾` のメニュー、絞り込みなし、ファイル名順）を加えたページャーを、それらを加える直前のページャーと同じ方法で比べました（2026-11-13、インデックスは計測前に埋まった状態）。

| ケース | 絞り込みと並べ替えあり | それ以前 |
|---|---|---|
| ARW, 1616x1080 | 19.6 / 32.2 | 22.3 / 31.0 |
| RAF, 4416x2944 | 65.8 / 79.2 | 65.3 / 76.4 |

p50 の差は ARW が -2.6 ms、RAF が +0.5 ms で、実行ごとのばらつきの範囲内です。`paint` と `present` は変わっていません。実行ごとの数値と計測条件は [`results.md`](../plans/_archived/20261113-gpui-filter-sort/results.md) にあります。

JPEG だけのフォルダー（閲覧専用）も、RAW のフォルダーと同じくプリフェッチのリングからページを送ります（2026-11-23、`--auto` で既定のウィンドウ、1 秒に 1 回のキー入力、リングありと `--no-prefetch` をそれぞれ 3 回、同じセッションで ARW のフォルダーを物差しに計測、3 回の p50 / p95 の `keypressToPixels` の中央値。ファイルはすべてベースライン JPEG で、1/8 か 2/8 でデコード）。

| ケース | プリフェッチあり | `--no-prefetch` | リングなしの `decode` p50 |
|---|---|---|---|
| ARW, 1616x1080（物差し） | 12.3 / 19.5 | 19.6 / 25.8 | 6.7 |
| Leica M11-P の DxO 書き出し、36-50 MP | 9.7 / 108.7 | 114.8 / 176.2 | 105.1 |
| Sony ILCE-7M5 の書き出し、13-33 MP | 12.6 / 19.2 | 50.2 / 62.5 | 29.6 |

既定のリングありでは、ほぼすべてのページがリングから出るので、p50 は ARW の物差しと同程度かそれ以下になります。Leica のフォルダーは 9〜10 ms で物差しより低く、Sony のフォルダーは 12.6 ms で物差しの実行ごとのばらつき（12.3〜13.6 ms）の範囲内です。リングにないページ（リングのデコードより速く送ったときや、離れたファイルへの移動）はデコード全体を払います。50 MP の JPEG では p50 が約 115 ms です。10-28 MB のファイルのエントロピー復号は出力の縮小率では減らないためです。fancy upsampling を切り、高速な整数 IDCT にしても `decode` は変わりませんでした（中央値 96.6 ms から 99.9 ms）。10 ファイルのフォルダーのリングありの p95 は、各回に 1 回あるこの外れです（n=8）。実行ごとの数値、500 ファイルのフォルダーの結果、計測条件は [`jpeg-preview.md`](../plans/_archived/20261123-todo-four-closeouts/jpeg-preview.md) にあります。

## フォルダースキャンのスループット

`handpic-cli scan` は、フォルダーの抽出（先頭部分に限った読み込み、メタデータの解析、404x270 のサムネイル）を専用の rayon プールで、データベースなしで実行します。12 コアの Apple Silicon Mac での結果:

| フォルダー | スレッド数 | 合計 | files/s |
|--------|---------|-------|---------|
| 1 つの ARW への 5000 個のシンボリックリンク、ウォームなページキャッシュ | 1 | 34.9s | 143 |
| 1 つの ARW への 5000 個のシンボリックリンク、ウォームなページキャッシュ | 8 | 5.35s | 935 |
| 1 つの ARW への 5000 個のシンボリックリンク、ウォームなページキャッシュ | 12 | 4.46s | 1121 |
| 48MB の異なるコピー 100 個、書き込み直後、ページキャッシュがコールドである保証なし | 4 | 0.44s | 230 |
| 48MB の異なるコピー 100 個、書き込み直後、ページキャッシュがコールドである保証なし | 12 | 0.19s | 529 |

サムネイルは 1 つ 19232 バイトで、5000 ファイルで約 96MB です。書き込み直後のコピーの列を 5000 ファイルに外挿すると、12 スレッドで 9.5s、4 スレッドで 21.7s になりますが、実際のコールドな読み込みのフォルダーでそれが成り立つかは、これらの数字からはわかりません。1 スレッドでは間に合いません（34.9s）。コア数より多いスレッドは役に立たず、16 スレッドは 12 スレッドと変わらないうえ、1 ファイルあたりの p95 が 2 倍になりました。実際のコールドな読み込みではこの外挿は成り立ちません。後述の「Windows の実フォルダー」を参照してください。

ここで計測できていないのは、5000 個の異なるファイルからなる実際のフォルダーです。ここでの書き込み直後のコピーのフォルダーはどれも `cp` による 100 個のコピーを 1 回スキャンしたもので、コールドである保証はなく、コピーは書き込んだ直後なのでページキャッシュ上でまだウォームだった可能性が高いです。また、フォルダーは書き込んだ順にスキャンしたため、スレッド数が多いほど有利に出ています。カードリーダーや遅い外付けディスクでは、いずれにせよスキャンはディスク律速になります。

### Windows の実フォルダー

スレッド数を変えて計測すると、コールドなスキャンのコストがドライブにあることがはっきりします。2026-09-22 に、Windows 11 Home のマシン（i7-13700）で、`x86_64-pc-windows-gnu` 向けにクロスビルドしたリリース版の `handpic-cli scan` で、DRAM レスの QLC SATA SSD（Crucial BX500 4TB）にある Sony ARW の実際のフォルダーを読み込んで計測しました。実行ごとに、起動後一度も読み込んでいない別のフォルダー（同じドライブ上）を使い、すべての実行がエラー 0 件で終わりました。

| スレッド数 | ファイル数 | 合計 | files/s | ワーカー上の 1 ファイルあたり（平均 / p95） |
|---------|-------|-------|---------|-----------------------------------|
| 1 | 1337 | 41.08s | 33 | 30.7ms / 58.2ms |
| 4 | 1415 | 27.34s | 52 | 77.0ms / 103.5ms |
| 8 | 1520 | 29.47s | 52 | 154.9ms / 196.8ms |
| 22 | 1545 | 22.90s | 67 | 324.2ms / 369.5ms |

スループットは 4 スレッド以上で約 50-67 files/s で頭打ちになり、ワーカー上の 1 ファイルあたりの時間はスレッド数を 2 倍にするたびにおよそ 2 倍になります。ワーカーが 1 つの共有資源、つまりドライブを待って並んでいるということです。DRAM レスの QLC SATA SSD はコールドなランダム読み込みが遅い SSD です。マッピングテーブル用の DRAM がないため余分な NAND の読み込みが必要で、QLC は読み込みのレイテンシーが高く（書き込んでから時間が経ったデータほど悪化します）、SATA にはコマンドキューが 1 つしかありません。1 スレッドでは 1 ファイルあたり約 30ms かかり、そのうち推定で約 10ms が CPU（ウォームなキャッシュでの実行から）、約 20ms がドライブ待ちです。原因は Handpic のコードではなくドライブで、スレッドを増やしてもほとんど効果はありません。

同じマシンの起動用 NVMe ドライブ（Crucial P5、DRAM 付きの TLC）は計測していないので、NVMe と SATA の比較はありません。計測ではなく予想としての回避策は、セレクトするフォルダーを NVMe ドライブ（内蔵、または UASP 対応の外付け USB NVMe ケース）に置くことです。5Gbps の USB 経由でも数倍速くなるはずです。

その後、先頭 1MiB に限った読み込みとファイル全体の読み込みを、2026-11-23 に同じマシンと同じドライブで、リリースビルド、4 スレッドで比べました。実行ごとに、起動後一度も読み込んでいない別の Sony ARW のフォルダーを使い、それぞれ 1 回ずつ計測しました。先頭部分に限った読み込みは `handpic-cli scan`、ファイル全体の読み込みはコミットしていない使い捨てのテストでの `std::fs::read` + `arw::parse` + `thumbnail_jpeg` です。マシンはほかのセッションの cargo のビルドと共有しており（CPU 負荷がときどき約 100%）、アイドルを待たずに計測しました。

| 読み込み | ファイル数 | 合計 | files/s | 読み込んだ量 |
|------|-------|-------|---------|------|
| 先頭 1MiB | 415 | 4.04s | 103 | 未記録 |
| 先頭 1MiB | 373 | 6.17s | 60 | 未記録 |
| ファイル全体 | 468 | 48.32s | 10 | 22,048MB |
| ファイル全体 | 324 | 36.84s | 9 | 16,402MB |

ファイル全体の読み込みは約 450MB/s で、ほぼ SATA の転送速度です。先頭部分に限った読み込みより 6-10 倍遅くなります。ウォームな状態で繰り返しても、同時に走っていた負荷のため速くなりませんでした（先頭部分に限った読み込みで 44 files/s、ファイル全体で 8 files/s）。1 / 4 / 8 / 22 スレッドの比較は上の 2026-09-22 の表で、NVMe ドライブはまだ計測していません。

### シャープネスのスコア計算のコスト

シャープネスのスコア計算は、各ファイルの抽出に埋め込みプレビューのグレースケールのデコードを加えます。12 コアの Apple Silicon Mac で、リリースビルドの `handpic-cli scan` を、α7 V の ARW（1616x1080 のプレビュー）1 つへの 1000 個のシンボリックリンクに対してウォームなページキャッシュで実行し、変更の前後を交互に計測しました。

| スレッド数 | 実行回数 | ワーカー上の 1 ファイルあたり、変更前（平均 / p95） | 変更後（平均 / p95） |
|---------|------|------------------------------------------|--------------------|
| 1 | 2 | 7.2-7.5ms / 7.6-7.9ms | 10.4-10.7ms / 10.9-11.2ms |
| 8 | 3 | 8.6-9.1ms / 12.1-13.3ms | 12.3-17.1ms / 15.7-22.0ms |

1 スレッドで 1 ファイルあたり約 +3.2ms（約 +45%）です。シンボリックリンクは 1 つのファイルを繰り返すので、これは IO のばらつきのない CPU のコストです。その後スコアは 1 回目のパスから 2 回目のパスに移ったため（後述の「どのパスがどのコストを担うか」を参照）、`handpic-cli scan` は「変更前」の列に戻り、約 3ms は 2 回目のパス（アプリの `scan faces`。full-eye-sharp-only の計画で削除するまでは `handpic-cli candidates` も）にかかるようになりました。

### 顔検出のコスト

スキャンは、目でシャープネスのスコアを取る前に、各埋め込みプレビューで YuNet（2023mar、`tract-onnx` 経由）を実行します。信頼できる AF 点の周りの 480x480 の切り出しは 320x320 の入力に縮小し、AF 点がなければ正立させたプレビュー全体を 640x448 の入力に縮小します（後述の「プレビュー全体での検出率（Windows 11）」を参照）。この検出は現在 1 回目ではなく 2 回目のパスで行います（後述の「どのパスがどのコストを担うか」を参照）。この節のうち「プレビュー全体での検出率（Windows 11）」より前の Linux WSL2 での計測はその移動と入力の拡大より前のもので、多くは 320x320 の検出を `handpic-cli scan` の中で時間を測っています。「プレビュー全体での検出率（Windows 11）」と「プレビュー全体の探索での DCT で縮小したデコード（Windows 11）」は 2 回目のパス（`handpic-cli detect` と `handpic-cli candidates`）の時間を測っています。最初の計測は Linux WSL2 のマシン（24 スレッド）で、リリースビルド、合成した入力（OpenCV のサンプル画像 `lena.jpg` と `messi5.jpg` を長辺 1616 px に拡大したもの）、1 スレッド、ウォームアップ 1 回の後の 30 回の実行です（時間にはモデル入力への縮小を含みます）。

| 入力 | 平均 | 中央値 | p95 |
|-------|------|--------|-----|
| 1616x1616 | 18.2ms | 17.8ms | 21.5ms |
| 1615x1008 | 17.1ms | 16.9ms | 18.7ms |

モデルの実行計画を組み立てる最初の呼び出しは 46ms かかりました。同じマシンでの、strip していないリリースバイナリのサイズ:

| バイナリ | 変更前 | 変更後 |
|--------|--------|-------|
| `handpic-cli` | 1.7 MB | 31.3 MB |

コールドな状態からの `cargo build --release -p handpic-cli` は 10.8s から 140s になりました。

#### プレビュー全体での検出率（Windows 11）

信頼できる AF 点のないファイル（Leica M のすべてのファイル、Sony のマニュアルフォーカス）は、正立させたプレビュー全体から顔を探します。この探索は現在、320x320 の正方形ではなく 640x448 の入力（縦位置のフレームでは 448x640、`faces::WHOLE_INPUT`）を YuNet に渡します。そのため 2112 px のプレビューの縮小率は 6.6 倍ではなく 3.3 倍になり、3:2 のフレームは入力の 3 分の 1 を余白にせずに埋めます。信頼できる AF 点の周りの切り出しは 320 px の入力のままなので、ピント候補の判定は変わりません。`handpic-cli candidates` は、ラベル付きの 9 個のフォルダーと 2134 個の ARW のフォルダーで、変更前と変更後で同じファイルごとの行、AUC、適合率、カバー率を出力しました。

2026-10-06 に Windows 11（Intel Core i7-13700、24 ハードウェアスレッド、32 GB）で、リリース版の `handpic-cli`、ローカルの NTFS ドライブから読み込み、ウォームなページキャッシュで、変更前と変更後を交互に実行して計測しました。検出率は、146 個の DNG のフォルダーから均等に選んだ M11-P の DNG 36 個とブランコのグループ `L1005161.DNG` を手で数えたものと比べています。36 個のうち 34 個に顔が写っており、顔は全部で 71 個です（約 40 px 未満の顔、フレームで切れた顔、隠れすぎた顔は数えていません）。見つかった顔は `handpic-cli faces` の画像で目視で確かめました。どの枠も顔の上にあり、数えられる顔のない 2 ファイルには何も付きません。

#### 目の開閉のモデルの調査（Windows 11）

YuNet の 5 つのランドマークにはまぶたの点がないため、閉じた目を見分けるには、AF 点に最も近い顔に 2 つ目のモデルを実行する必要があります。2026-10-07 に、Windows 11（Intel Core i7-13700、24 ハードウェアスレッド、32 GB）で、リリースビルド、1 スレッドで、手でラベルを付けた 504 個の顔に対して 4 つの候補を計測しました。α7 V の 2134 個の ARW のフォルダーから 432 個（無作為に 240 個、閉じた目に寄せて 192 個）、M11-P の 146 個の DNG のフォルダーから 72 個です。顔 1 つあたりの時間には、フルサイズの正立したプレビューからの切り出しとモデル入力への縮小を含みます（目ごとのモデルは顔 1 つで 2 回実行）。AUC は、顔の 2 つの目のうちより閉じている方のスコアを、閉じている / 開いているという手のラベルと比べたものです。4 つとも `default-features = false` の `tract-onnx` で読み込めます。MediaPipe のものは Google の TFLite ファイルを ONNX に変換したものです（tf2onnx、tflite2onnx）。

#### 表示時の閉じた目の判定（Windows 11）

アプリは閉じた目を Face Landmarker v2 で、スキャン時と、表示中のファイルについてはその都度判定します。エンジンの `ondemand::read_eyes` は、`f` のオーバーレイの下でファイルが表示されたときに、スキャンのどちらのパスとも別に、描く顔のパーツのために実行されます。判定する顔は 1 つで、信頼できる AF 点に最も近い顔、AF 点がなければ 0.8 以上の顔のうち最も大きいものです。顔の辺が 60 px 未満なら判定しません。その顔について、2 回目のパスがピント候補の判定のためにすでに実行しているメッシュから目のアスペクト比と頭の向きを保存し（モデルの実行は増えません）、メタペインの `Eyes` の行とフィルターメニューの `Eyes` セクション、ストリップの閉じた目のマーク、MCP の `get_view` ツールの `eyes` はそれを読みます。その都度の実行は、メッシュの 478 点を保存しないため `f` のオーバーレイのメッシュの出どころであり、目の状態が保存されていないファイルでの `get_view` のフォールバックであるだけです。オーバーレイがオンの間、表示中の RAW ファイルについてだけ実行されるので、スキャンが目のアスペクト比と頭の向きを保存したファイルは、オーバーレイがオフならモデルを 2 回実行することはなく、それを待つ読み手もありません。2026-10-07 に、同じ Windows 11 のマシンで、リリースビルド、1 スレッドで、`main` の `392f9c25` で計測しました（変更前のサイズは、モデルを呼ぶ前の同じ日のビルドのものです）。

| バイナリ | 変更前 | 変更後 |
|--------|--------|-------|
| `handpic-cli` | 24.6 MB | 29.6 MB |

`include_bytes!` で埋め込む 4.9 MB の ONNX ファイルの分だけ増えました。

モデル自体（切り出し、縮小、実行、目のアスペクト比）は、ラベルを付けた 504 個の顔に `handpic-cli eyes` を実行して、平均 34.6ms、中央値 34.1ms、p95 41.2ms でした。実行計画を組み立てて 1 回実行する最初の呼び出しは 182ms でした。調査の 50.9ms より速いのは、調査では呼び出しの合間にほかの 3 つのモデルを実行していたためです。

実行中のアプリでプレビューが出てからオーバーレイが出るまでの時間（`Handpic.log` の `eyes` の時間計測の行）はまだ計測していません。GUI が必要なためです。

精度は `handpic-core` 自体で測りました（`handpic-cli eyes` は調査と完全に同じ目のアスペクト比を出します）。ラベルを付けた 253 個の顔（閉じているのは 57 個）で顔の AUC は 0.974、しきい値（比が 0.137 以下なら閉じている）で正解率 0.957、適合率 0.94、再現率 0.86 です。アプリが判定する 60 px 以上の 246 個の顔では、AUC 0.974、正解率 0.955、適合率と再現率は同じです。ARW の無作為の標本だけでは 0.918（適合率 0.85、再現率 0.73）、DNG の顔では 0.986 です。伏し目は閉じていると判定されます。

判定した顔の頭の向き（メタ情報ペインの `Yaw`、`Pitch`、`Roll` の行）は、MediaPipe の顔のジオメトリの処理を移植したもので、同じモデルの実行で得た点から求めます（`crates/core/src/pose.rs`）。そのためモデルの実行もデコードも増えません。計算は顔 1 つあたり中央値 8.2µs（p95 18µs、最大 26µs。M11-P のフォルダーで判定した 72 個の顔、それぞれ 200 回、1 スレッド、リリースビルド）です。

CLI のバイナリはコードの分だけ増え（2026-10-07、`main` の `9048e952` と、頭の向きの前のコミット `bde23660` の比較）、`handpic-cli` で 29,556,224 B から 29,577,728 B（+21,504 B）になりました。

精度は、同じ 2 つのフォルダーから（フォルダーにあるより多く横や斜めを向いた顔と傾いた顔を含めて）選んだ 190 個の顔のうち読み取れる 159 個に、目で見て大まかな分類と向きのラベルを付けて比べました（正解の角度はなく、ラベルはエージェントが付けたもので、まだ確認されていません）。符号は、横を向いた 81 個のうち 76 個（ヨー、94%）、上か下を向いた 77 個のうち 73 個（ピッチ、95%）、傾いた 18 個のうち 15 個（ロール）で合っています。分類（ヨーは 15 度未満が正面、15-50 度が斜め、50 度を超えると横顔。ピッチとロールは 15 度以内が水平）は、ヨーで 68%、ピッチで 79%、ロールで 89% 一致します。ヨーの不一致はほとんどが正面と斜めの境目で、正面とラベルを付けた 28 個の顔が 15-42 度と読まれました。正面に見える程度の回転で、正面の顔が横顔と読まれたことはありません。およそ 70 度を超える横顔とスポーツ用サングラスでは粗く、横顔のヨーは 90 度を超えて読まれることがあります。2 つのフォルダーで判定した 2024 個の顔のうち 15 個は上下逆に当てはまり（ロールが 90 度を超える。後頭部、耳、ぶれ）、頭の向きを出しません。MediaPipe の 63 度のカメラの代わりにレンズ自体の画角を使っても、符号の一致数はどれも変わらず（符号が変わるのは 0 度から 8 度以内の角度だけです）、角度は中央値でおよそ 1 度動くだけです。

### どのパスがどのコストを担うか

シャープネスのスコアが 2 回目のパスに移ったため、1 回目のパス（`handpic_core::scan::extract`、`handpic-cli scan`、アプリの `scan extract` の行）はプレビューを読み込み、サムネイルとメタデータだけを計算します。2 回目のパス（`handpic_core::scan::extract_analysis`、アプリの `scan faces` の行）はプレビューをもう一度読み込み、ピント候補の判定とシャープネスのスコアの両方を計算します。

| コスト | 以前のパス | 現在のパス |
|------|-------------|----------|
| 先頭部分に限った読み込み、メタデータの解析、サムネイル | 1 回目 | 1 回目 |
| シャープネスのスコア（手がかりの RGB のデコードの BT.601 の輝度 + 範囲、1616x1080 の ARW のプレビューで約 3ms。手がかりが RGB をデコードしなかった場合はグレースケールのデコード + 範囲、約 6ms） | 1 回目 | 2 回目 |
| 信頼できる AF 点がない場合のプレビュー全体での顔の探索（320x320 で約 17ms、Windows の 640x448 で約 64ms。その前のデコードはフルサイズの約 14ms ではなく 3/8 の約 5ms） | 1 回目 | 2 回目 |
| ピント候補の判定（切り出しの検出 + フェイスメッシュの目の領域、目の範囲への切り戻し） | 2 回目 | 2 回目 |
| HDR PQ の CR3 の HEVC のデコード（65-125ms） | 1 ファイルにつき最大 3 回 | 1 ファイルにつき 2 回（サムネイル、解析） |
| 閉じた目の判定（Face Landmarker v2、顔 1 つあたり約 35-45ms） | - | メッシュと姿勢の計算はピント候補の判定のために 2 回目のパスでも実行（1 スレッドで顔 1 つあたり約 29ms）し、AF の顔の目のアスペクト比と頭の向きをメタペインと `Eyes` フィルターのために保存。その都度の判定（`ondemand::read_eyes`）は `f` のオーバーレイがオンの間、表示中の RAW ファイルについてだけ、そのメッシュの出どころと `get_view` のフォールバックとして実行 |

信頼できる AF 点がなく確かな顔があるファイルは、2 回目のパスでプレビューを 3 回ではなく 2 回デコードします。プレビュー全体の探索のための 3/8 のデコードと、フルサイズの RGB のデコード 1 回で、シャープネスのスコアは自前のグレースケールのデコードの代わりにその RGB の BT.601 の輝度で取ります（`FACES_VERSION` 13）。2026-11-24 に Windows 11（i7-13700）上で、リリースビルド、1 スレッド、ウォームなキャッシュ、交互に 2 回ずつ実行した `handpic-cli features <dir> 1` では、それらのファイルの `analysis_ms` の中央値が `2026-02-01`（72 ファイル）で 286.6 -> 245.2ms、`2026-09-05`（204 ファイル）で 226.5 -> 211.3ms で、1 ファイルあたりの短縮の中央値は 13.4ms と 16.2ms でした。これらの Leica M11-P の DNG ではスコアはまったく変わりませんでした。`docs/plans/_archived/20261123-todo-four-closeouts/no-af-decode.md` を参照してください。

信頼できる AF 点があるファイルは、`FACES_VERSION` 17 から 2 回目のパスでプレビューを 1 回だけデコードします。シャープネスのスコアは、同じ AF 点と瞳 AF の枠のまま、自前のグレースケールのデコードの代わりに手がかりのフルサイズの RGB のデコードの BT.601 の輝度で取り、RGB のデコードに失敗したファイルは以前どおり自前のデコードでスコアを取ります。2026-11-28 に Windows 11（i7-13700）上で、リリースビルド、1 スレッド、ウォームなキャッシュで、`2026-09-19` の信頼できる AF 点がある 1616x1080 の ARW のプレビュー 282 個では、グレースケールのデコードと範囲が中央値 6.4ms、それに代わる画像全体の輝度と範囲が 3.1ms で、1 ファイルあたりの短縮の中央値は 3.2ms（2 回目の計測で 3.0ms）でした。スコアは中央値で 1.4% 動き（輝度のほうが高い）、バースト内の順位はまったく動きませんでした（50 個のバーストすべてで Spearman 1.000、最上位のフレームもすべて同じ）。信頼できる AF 点も確かな顔もないファイルは、以前どおりグレースケールのデコードでスコアを取ります。`docs/plans/_archived/20261128-af-luma-reuse/luma-reuse.md` を参照してください。

1 回目のパスはサムネイルができた順に小さなまとまり（10 件）で行を書き込むため、サムネイルは読み込みとサムネイルのエンコードの速さで表示され、フォーカスマークは 2 回目のパスの間に埋まっていきます。上の「シャープネスのスコア計算のコスト」、「顔検出のコスト」、「ピント候補のパス」の数字は、2 回目のパスの時間を測った「顔検出のコスト」の 2 つの Windows 11 の小節と「ピント候補のパス」のフェイスメッシュの 2 つの段落を除き、移動の前に計測したものです。「顔検出のコスト」にある `handpic-cli scan` の「変更後」の数字には、現在そのパスが担っていないコストが含まれています。

アプリでは両方のパスが通常より低い OS の優先度で動き（Windows では 1 回目が `THREAD_PRIORITY_BELOW_NORMAL`、2 回目が `THREAD_PRIORITY_LOWEST`、macOS では両方とも `UTILITY` の QoS クラスで 2 回目は相対優先度 -5、Linux では nice 値がそれぞれ 5 以上と 10 以上）、表示中のファイルとストリップに見えているセルを先に処理します。`handpic-cli scan` は通常の優先度でファイル名順に動くので、その数字は上の表と比べられるままです。

まだ計測していないもの: 優先度を下げて画面上のファイルを先に処理するキューでの `scan extract` / `scan faces` の全体時間です。これらは、アプリで実際のフォルダーを使った手作業の計測が残っています。

## インデックス済みフォルダーを再び開く

インデックスがすべてそろったフォルダーを 2 回目に開くときは抽出を行いません。すべてのファイルを stat し、行を突き合わせ、問い合わせるだけです。5000 ファイルのフォルダーでの結果:

| 処理 | 目標 | 実測 |
|------|--------|----------|
| 初回に開く、フルスキャン（5000 ファイル、10 スレッド、エラー 0 件） | - | 5.55s |
| 2 回目に開く（stat + 突き合わせ + 問い合わせ、インデックス済み） [^1] | 3s | 34.4ms |

どちらの行も **1 つの実際の ARW を指す 5000 個のシンボリックリンクで、ページキャッシュがウォームな状態** で計測したので、上の表と同じ注意が必要です。2 回目に開く処理は stat と問い合わせの数字で、読み込みのベンチマークほどシンボリックリンクによって有利にはなりませんが、キャッシュされた 1 つの inode のメタデータを 5000 回引くのは、カード上の 48MB の異なる 5000 ファイルのメタデータを引くより安上がりです。初回のスキャンは上のスキャンのスループットの表と同じフォルダーと手順で、その表に行のない 10 スレッドで計測しました。異なるファイルからなる実際のフォルダーについては、上の「Windows の実フォルダー」を参照してください。カードリーダーや遅い外付けディスクでは、いずれにせよ初回のスキャンはディスク律速になります。

[^1]: コミット前に削除した一時的な `#[ignore]` 付きのテストで計測したため、コミットされたツリーからはこの数字を再現できません。

### 自分のフォルダーで計測する

Handpic は自分のスキャンの時間をログに書くので、これらの数字はどのフォルダーでも再現できます。設定の `Cache` ページでキャッシュを消去して次に開くときが初回のスキャンになるようにし、フォルダーを開き直します。次に終了してもう一度起動すると 2 回目に開く処理になり、`Handpic.log` を読みます（場所は[ログファイル](./usage.ja.md#機能)を参照）。

開くたびに、`scan list`（フォルダーの読み込み）、`scan reconcile`（インデックスに対するファイルの stat と、`todo` の数）、`scan sidecars` を書き、続いて抽出のパス全体を表し `files`、`done`、`errors`、`threads` の数を持つ `scan extract` と、2 回目のパスの `scan faces` を書きます。初回のスキャンの `scan extract` は `files` > 0 で、その前の 3 行とその `scan extract` の合計が初回のスキャンの合計です。

2 回目に開くときも同じ行を書きますが `todo=0` となり、その `scan extract` は `files=0 done=0` でほぼゼロの時間になります。キャッシュから開いたことを示すのは、行がないことではなく、この `files=0` の行です。その回の `scan list`、`scan reconcile`、`scan sidecars` の行を足してください。どの行も `in <n>ms` で終わり、ディレクトリ名を含み、タイムスタンプで 2 回の実行を見分けられます。

ページごとのレイテンシーはログではなく出力に書きます。Handpic をターミナルから起動すると、キーによるページ送りのたびに `page wait=… read=… decode=… orient=… hop=… frameWait=… paint=… present=… keypressToPixels=… jpegKB=… px=WxH decoded=WxH orientation=… source=… file=…` の行を標準出力に書きます（等倍の切り出しを表示した `z` では `zoom read=… decode=… orient=… keypressToPixels=…` の行。キーより前に先読みした切り出しの `read`、`decode`、`orient` はその先読みのものです）。`wait` はキーから読み込みの要求まで、`read`、`decode`、`orient` はプレビューの読み込み（スキャンの読み込みの一時停止を含みます）、デコード、正立への回転（先読み済みのプレビューである `source=prefetch` ではすべて 0）、`hop` はウィンドウへの受け渡し、`frameWait` は次のフレームまでの待ち、`paint` は描画、`present` はフレームの提示で、`keypressToPixels` はキー入力から提示されたフレームまでです。`px` は埋め込みプレビューの大きさ、`decoded` はそれをデコードした大きさです。Handpic は画面上の写真の領域を覆う最小の 8 分の n の大きさでプレビューをデコードするので、小さなウィンドウで大きなプレビューを表示すると `px` より小さくなります。キーによらないページ（ストリップのクリックやフォルダーを開いたとき）は何も書きません。`q` での終了時（または `--auto N` の終了時）には段階ごとの要約の表を書き、`--auto N` はタイマーで N ファイルを送って終了します。

Windows のリリースビルドは自分のコンソールを開かないため、標準出力はパイプかファイルを通したときだけターミナルに届きます。Git Bash では `mise run app:release -- <folder> --auto N | cat`、PowerShell では `mise run app:release -- <folder> --auto N | Out-Host`、cmd では `mise run app:release -- <folder> --auto N > timing.txt` のように実行してください。そうしないと、これらの行は失われます。

## 等倍ピントチェックの経路

1 回のズームのキー入力の読み込みとデコードを、Apple Silicon Mac で、α7 V の ARW 1 つ（Orientation 8、`JpgFromRaw` 7008x4672 ベースライン 4:2:2、5.76MB）で計測しました。**実際のファイル 1 つ、ウォームなページキャッシュ、プロセス内、リリースビルド、n=20、中央値です。** CLI とアプリの両方が呼ぶ関数に対して計測しています。正立への回転と描画は含みません。アプリはそれらを `zoom` の行として書き出します（上の「自分のフォルダーで計測する」を参照）。Windows でのエンドツーエンドの数字は下の「`z` の前に切り出しを先読みする（Windows 11）」にあります。

| 処理 | 中央値 |
|------|--------|
| 5.76MB の `JpgFromRaw` の範囲読み込み（`reader::read_full`） | 0.7ms |
| フォーカス位置での切り出し、各辺 512 / 1024 / 2048（`partial::decode_focus_crop`、RGBA） | 18.4 / 21.5 / 29.8ms |
| 4672 行の JPEG の 300 / 2336 / 4400 行目での 1024 の切り出し（`partial::decode_crop`、RGB） | 10.8 / 27.3 / 44.1ms |

切り出しのサイズはほとんど影響せず、大半を占めるのは切り出しの **行** です。ベースライン JPEG では `jpeg_skip_scanlines` も読み飛ばす行をすべてエントロピー復号するので、フレームの下のほうにあるフォーカス位置は上端の 4 倍のコストがかかり、44ms では 50ms の予算のうちほかの処理に回す分がほとんど残りません。その切り出しを `mozjpeg::Compress` の既定値で JPEG に再エンコードすると q85 で 49ms かかり、その前のデコードより遅くなりました。

### `z` の前に切り出しを先読みする（Windows 11）

コストは切り出しの行で決まるので、アプリは `z` が求める前に切り出しを読むようになりました。表示中のファイルのプレビューが画面に出たら、そのファイルの切り出しをバックグラウンドで読み、`z` はすでに持っている切り出しを描きます。等倍表示中は、ページ送りの方向の次のファイルの切り出しを読み、そのファイルへ送ると読み込みなしで表示します。プレビューの先読みと同じ条件に従い、スキャンのパスの実行中は動かず、`--no-prefetch` ではプレビューのリングと一緒に止まります。

深い行 / 浅い行の計測です。GPUI のアプリ、リリースビルド、α7 V の ARW（`JpgFromRaw` 7008x4672 ベースライン 4:2:2、Orientation 8）、既定の 1600x1000 のウィンドウで、ファイルごとに `z` を 1 回（`z`、900ms、`z`、300ms、`→`、700ms）、1 回の実行で 19 ファイルのセットに 20 回押し（最後の 1 回は先頭のファイルに戻ります）、フォーカスの行の平均は深いセットで JPEG の高さの 0.94、浅いセットで 0.06、実行ごとに新しいインデックスで、スキャンは最初のキーより前に終わっています。**アイドル待ちはしていません。マシンはほかのセッションの cargo のビルドと共有でした。** 以前の実行は 2026-11-23 に最大 100 % ほどの負荷の下で取り、2026-11-24 の実行では各実行の直前に 2-50 %（5 回の平均）の CPU 負荷でした。

| 実行（各行 2 回） | `keypressToPixels` p50 | p95 | 50ms 超 | `decode` p50 |
|---|---|---|---|---|
| 深い行、以前（2026-11-23） | 72-77ms | 84-88ms | 40 回中 38 回 | 55-58ms |
| 深い行、`--no-prefetch`（2026-11-24） | 44-50ms | 54-65ms | 40 回中 15 回 | 32-39ms |
| 深い行、先読み（2026-11-24） | 11.3-11.5ms | 18.0-18.7ms | 40 回中 0 回 | 31-32ms |
| 浅い行、以前（2026-11-23） | 32-35ms | 36-37ms | 40 回中 0 回 | 18-19ms |
| 浅い行、`--no-prefetch`（2026-11-24） | 21-27ms | 27-34ms | 40 回中 0 回 | 9-11ms |
| 浅い行、先読み（2026-11-24） | 10.5-12.9ms | 17.5-18.4ms | 40 回中 0 回 | 9.4-9.5ms |

先読みでは、どのキーでも切り出しはすでに手元にあり、フォーカスの行によらずキー 1 回のコストは 1 フレームです。`decode` は切り出しそのもののデコードで、先読みした切り出しではキーより前に済んでいます。`--no-prefetch` の実行が同じセッションでの「以前」です。2026-11-23 の数字より低いのは負荷の違いによるもので、読み込みが変わったのではありません。ページ送りは遅くなっていません。同じ実行の `→` の `page` の行は p50 9.5-12.4ms、p95 17.3-18.9ms（以前は 11.2-13.5 / 19.6-27.0ms）のままで、`→` の長押しも切り出しの読み込みの有無で同じでした（どちらも p50 10.6-11.5ms）。

もう一方の案は採りませんでした。JPEG にリスタートマーカーがない（DRI も RST もない）ので、深い行に届くにはその上の行をすべてエントロピー復号するしかありません。アプリはすでにフィット表示のプレビューを拡大して、切り出しが届くまでのプレースホルダーとして描いています。DCT スケールのデコードも速くなりません（上の「Fujifilm RAF（raw.pixls.us のサンプル、Windows）」を参照）。

先読みが扱わないもの: バックグラウンドの読み込みが終わる前に押した `z` は残りを待ちます。スキャンのパスの実行中の `z` は先読みされず、以前と同じコストがかかります。`--no-prefetch` の下の `z` も同じです。

## サイドカーのパスがフォルダーを開く処理に加えるもの

フォルダーを開くときは XMP のサイドカーの突き合わせも行います。ディレクトリを 1 回列挙し、見つかったサイドカーごとに `stat` し、アプリが前回見てから `(size, mtime)` が変わったものだけを解析します。

| 5000 ファイルのフォルダーを 2 回目に開く | 実測（中央値） |
|-----------------------------------|-------------------|
| フォルダーにサイドカーなし | 31.3ms |
| 5000 個のサイドカー、すべて stat に変化なし | 67.4ms |

**この 2 つの数字は上の 34.4ms とは比べられず、それに代わるものでもありません。** 別のフォルダーで計測したものです。`*.ARW` という名前の 1KB の通常ファイル 5000 個（シンボリックリンクでも実際の ARW でもない）を、ローカルの APFS ディスク上に置き、ウォームなページキャッシュで、Apple Silicon Mac で計測しました。計測した処理は、フォルダーを開くときに Rust 側が行うのと同じ一連の処理（列挙、すべてのファイルの `stat`、`reconcile`、サイドカーの突き合わせ、`entries`）で、コミット前に削除した一時的な `#[ignore]` 付きのテスト（リリースプロファイル、ウォームアップ 3 回の後の 7 回の中央値）で計測したため、どちらの数字もコミットされたツリーからは再現できません。これらがはっきり示すのはコストの形です。このマシンではサイドカーのパスは 2 回目に開く処理をおよそ 2 倍にし、5000 個のサイドカーで約 36ms を加えます。そのコストは解析ではなく列挙と 1 つずつの `stat` です。stat に変化がなければ何も解析しないためです。他のアプリのサイドカーでいっぱいのフォルダーを初めて開くときは解析のコストもかかりますが、計測していません。

## メモリーカードからのコピー

`Import…` は `handpic_core::copy` を通してコピーします。1 つのスレッドがカードを 8 MiB 単位で順に読み、最大 4 個のバッファーを、コピー先に書き込む 1 つのスレッドに渡します。書き込み側は各ファイルをフラッシュしてから本来の名前に変えます。エクスプローラーより速いとはうたっていません。これまでの唯一の計測では、コピー先のドライブが上限になっていたので、コピーの方法の差は見分けられず、エクスプローラー自体も計っていません。

約 44 MB の Sony ARW を、USB カードリーダー（exFAT）から Crucial BX500 4 TB SATA SSD（NTFS、使用率 96 %）へ、Windows 11 でコピーしました。各回は未読の 50 ファイル（約 2.2 GB）を使ったのでカードはコールドで読まれ、回の間には 60 秒の待ち時間を置きました。実行順に示します。

| 回 | 方法 | MB/s |
|----|------|------|
| A | パイプライン、8 MiB × 4 | 21.6 |
| B | `robocopy /J` | 14.4 |
| C | `robocopy`（バッファーあり） | 12.1 |
| D | パイプライン、32 MiB × 2、`FILE_FLAG_SEQUENTIAL_SCAN` | 12.9 |
| E | パイプライン、8 MiB × 4、ファイルごとのフラッシュなし | 11.1 |
| F | パイプライン、8 MiB × 4、`FILE_FLAG_SEQUENTIAL_SCAN` | 9.6 |
| – | 読むだけ、`dd bs=8M` で `/dev/null` へ | 134.7 |
| G | パイプライン、8 MiB × 4（A の繰り返し） | 8.1 |

方法にかかわらずスループットは回を追うごとに下がりました（A と G は同じ設定です）。カードだけを読むと 135 MB/s 出ています。BX500 は DRAM を持たず、ほぼ満杯で、書き込みが続くと書き込みキャッシュを失います。それ以前の 4.5 GB の実行では、コールドで 45 MB/s、直後の繰り返しでは 9 MB/s しか出ませんでした。`FILE_FLAG_SEQUENTIAL_SCAN` もファイルごとのフラッシュの省略も効果がなかったので、どちらも採用していません。

### 自分のカードでエクスプローラーと比べる

`handpic-cli copybench <src-dir> <dst-dir> [chunk-mib] [buffers]` は、`src-dir` の下のすべての RAW と JPEG を、アプリと同じパイプラインで `dst-dir` に階層なしでコピーし、ファイル数、バイト数、秒数、MB/s を表示します。実際のインポートは同じ数値を `Handpic.log` の `import:` の行（`mb_per_s=`。[Handpic の使い方](./usage.ja.md#機能)を参照）に書きます。同じ数のファイルをエクスプローラーでコピーした時間と、そのどちらかを比べます。公平に比べるには次の点に注意してください。

- NVMe ドライブや空きの多い SSD など、カードより速いコピー先を使います。遅いコピー先では、そのドライブの速さを計ることになります。
- カードを挿してからまだ読んでいないファイルを使います。読んだファイルはカードではなく OS のキャッシュから返ります。
- コピー先が前のコピーでまだ忙しい間はカードの時間を計らず（そのように計った読み取りは 16〜22 MB/s でした）、回の間にはドライブを休ませます。
