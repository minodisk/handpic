## Round 1

**Reviewed commit**: `e73ca67dc599fe842054a92f007bb3be65ff9dc8` perf(app): read the 1:1 crop ahead of z

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/src/zoom.rs:458-471]**: When a neighbour's crop lands after the page has already moved past it while zoomed, `ahead_arrived` puts it in the `ahead` slot and does not draw it. This breaks the "A held key draws each stale crop before chasing the current one" rule, which `docs/agents/app.md:2894` still states. Here is how it happens while zoomed with a held `→` key. On `b`, the read ahead of `c` is in flight. The key moves to `c`, and `page` asks for nothing because one read is already in flight. Before `c`'s crop lands, the key moves on to `d`. `c`'s crop then lands, `current` is `d`, and the crop is parked in the slot. Then `wanted` asks for `d`. The screen keeps showing `b`'s crop until `d` arrives. Before this change, `c`'s read was the current page's read, so `arrived`'s zoomed-stale branch would have held and drawn it on the way. The parked crop is also a file the page has already passed, so it is never used. The next `page` releases it, which goes against the plan's "each is dropped when the page ... no longer matches it". `zoomed_a_neighbours_crop_landing_after_a_page_elsewhere_asks_for_the_current` (line 1006) currently asserts this parking (`release == None`). Suggested fix: have `Flight` record the `seq` the read was asked on. In `ahead_arrived`, if the page has moved since that `seq` and `path` is not current, treat the crop the same way as `arrived`'s zoomed-stale branch: replace `held` with it under an old `seq`, so `holds` / `placeholder_fits` stay correct and the crop is drawn as a stale frame. Keep using the `ahead` slot only while the page has not moved. Then update that test, and add a held-key case like `a_held_key_holds_each_stale_crop_and_asks_once_per_arrival` that goes through a read ahead.

## Round 2

### Findings

1. **[crates/app/src/zoom.rs:465-480]**: (repeat of Round 1 item 1, narrowed) The new branch is too broad. It draws a neighbour's crop whenever the page has moved since the read was asked and the neighbour is not current. That includes pages that never landed on the neighbour, so the 1:1 view can draw a file the user never paged onto. For example: zoomed on `a`, the read ahead of `b` is in flight, and the user presses `←` (or clicks `d`, or a refilter moves the page). When `b`'s crop lands, it replaces `a`'s held crop and is drawn until the current page's crop arrives. That is a wrong-direction or skipped file. `arrived`'s zoomed-stale branch, which this one claims to mirror, only ever draws a page that was current at some point. The updated test `zoomed_a_neighbours_crop_landing_after_a_page_elsewhere_asks_for_the_current` (line 1029, a→c without visiting `b`) now asserts this behaviour (`crop() == Some(&8)`). The `docs/agents/app.md` rule ("lands after the page has moved past it") describes the same over-broad condition. Fix: record on the `Flight` that the page passed through the neighbour. Store the ahead path in `Flight`. In `page`, set a `passed` flag when `current` equals that path. In `ahead_arrived`, take the stale-draw branch only when `passed` is set and the path is not current, and keep the held crop's `seq` at a value that can never be current again. Otherwise release the crop (do not park it, since the page has left the position it was read for). Restore that test to expect `a`'s crop to stay held with `b`'s released, add a reverse-key case, and narrow the `app.md` rule's wording to match.
