### Findings

1. **[crates/native/src/folderops.rs:1813, 1796, 1890]**: With `mcpAllowDestructive` off, `rename_folder` relies on the tree's inline editor, prefilled with the client's name, as the user's confirmation. That editor confirms on more than Enter, though. `start_rename` subscribes `InputEvent::Blur` to `rename_event(true, ..)`, and that commits whenever the window is active. A second `start_rename` (a slow click on another row) also calls `finish_rename(Decision::Confirm)` on the live edit. When the client calls `ask_rename`, the user is usually in the MCP client app, so the Handpic window is inactive and the blur is deferred. As soon as the user returns to Handpic and clicks anywhere outside the field (the strip, the preview, another tree row), the client's name is committed through `request_rename`. The user never pressed Enter and may never have read the prefilled name. This breaks the step's safety rule: nothing should run over MCP without either the grant plus a confirmed preview, or the user's own confirmation in the app. It also contradicts the tool description ("the user confirms with Enter"), `awaiting()`'s `next` text and `docs/agents/native-app.md:1040` ("the user's Enter renames, Escape cancels"). Suggested fix: mark an edit opened through `filled` (for example a flag on `Edit` or `InlineRename`). For such an edit, a blur and the implicit confirm in `start_rename` should cancel (or leave the edit open) instead of confirming, so only `PressEnter` renames. Add a unit test on the pure part (e.g. `commit` / `edit_outcome` or a new helper deciding the blur's decision for a filled edit). The user's own inline rename keeps its blur-confirms behavior.

### Fixes

1. Fixed: an edit opened through `filled` is now `InlineRename::asked`; its blur and a second `start_rename` cancel (`implicit`) instead of confirming, so only Enter renames. Unit test added in `rename.rs`; `docs/agents/native-app.md` updated.
