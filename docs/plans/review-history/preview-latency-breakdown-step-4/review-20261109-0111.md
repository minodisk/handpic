## Round 1

**Reviewed commit**: `248d8a263647887471dbe227c22c156786f90a87` feat(app): prefetch and keep the neighbours' decoded previews

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/ui/src/prefetch.ts:164]**: Previews over 16 MP cause a wasted read and decode on every page turn, then permanently lose the backward neighbour. `insert` adds only `victim === path` to `refused`, so a different entry it evicts is immediately eligible for `next()` again. In a view-only JPEG folder, `read_preview` returns the whole JPEG (`crates/core/src/reader.rs:50`), and `requestPrefetch` has no view-only guard. Paging forward through 24 MP files goes like this: turning to `i+1` keeps `i` (24 MP), and reading `i+2` makes 48 MP, so `i` is evicted. `next()` then re-reads `i`, the insert goes over the cap again, `i` evicts itself and is refused for the rest of the folder session. Each page turn therefore costs one full read and 24 MP decode that is discarded, and turning back is always a miss because every passed file is refused. A file over 32 MP costs a discarded read and decode per new neighbour. The `PREFETCH_PIXEL_CAP` comment ("the largest previews a culling folder has") and the learnings line ("Not a case any listed body reaches") only consider RAW previews, so they are wrong for JPEG folders. Suggested fix: do not re-read a file that was evicted for space while the current position stands, and do not make that exclusion outlive the position (for example, keep over-cap refusals separate from failures and drop them in `plan` when the path leaves `wanted`). Either that or skip the ring in view-only folders, with a test for two neighbours that cannot share the cap, and correct both comments.

2. **[crates/app/ui/src/main.ts:4355]**: `renameFile` updates `files`, `fileIndex` and the ring, but leaves `shown.path` on the old name, so `present` can file the shown bitmap under a path that now names a different photo. Rename the current file X to Y, rename another file Z to X, then jump to a file whose neighbours include the new X. `ring.keep("X", previous)` stores Y's bitmap as X, and turning to X draws the wrong photo from the ring. This is rare, but it is exactly the stale hit the ring must never produce. A page read in flight during the rename has the same problem through `timing.path` at line 3982. Suggested fix: when `shown?.path === path`, set `shown.path = newPath` beside the `ring.forget` call, and carry the new path through or discard the in-flight timing's path.

3. **[crates/app/ui/src/main.ts:4603]**: `ring.clear()` runs because a re-listing "may have changed any file's bytes" (`prefetch.ts`, learnings), but the on-screen bitmap survives it and `present` hands it back through `ring.keep` on the next page turn. If the current file was replaced on disk, turning away and back draws the old decode with no read, where before this PR the return trip re-read the file. Suggested fix: mark `shown` as not returnable at the `clear()` sites (for example a `keepable` flag on `shown` that `present` checks before `ring.keep`).

4. **[crates/app/ui/src/main.ts:2655]**: When `refilter` keeps the current file and does not call `show()`, a filter or sort change gives the current file new neighbours, but nothing re-plans the ring or reads them. The next page turn is a guaranteed miss even though the app has been idle, and `wanted` still names the old neighbours until then. Suggested fix: call `requestPrefetch()` in that branch (it already re-plans and guards on the scan and the in-flight request).
