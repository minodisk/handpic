### Findings

1. **[crates/backend/src/mcp.rs:440 (`ExifArgs`)]**: `ExifArgs` is a typed struct without `#[serde(deny_unknown_fields)]`, so serde silently drops an unknown section name. A call such as `set_filter {"exif": {"model": ["ILCE-1"]}}` reaches the companion as `{"exif": {}}`. `wanted_filter` treats that as given with no change, and `set_filter` answers `Ok(None)`, so the tool replies with the unchanged `get_view` as if it had worked. The companion's own refusal (`exif sections must be among camera, lens, ...`, asserted in `set_filter_refuses_what_the_menu_does_not_offer`) can never be reached through the real tool. Fix it with `#[serde(deny_unknown_fields)]` on `ExifArgs`, so rmcp's parameter deserialization refuses the call, and add a backend test like `filter_args(json!({ "exif": { "body": [] } })).is_err()`. Alternatively, take `exif` as a `Map<String, Vec<String>>` and let the companion's check run. The same silent drop applies to a misspelled top-level `FilterArgs` field next to a valid one, e.g. `{"flag": ["picked"], "stars": [5]}` applies only the stars. Consider `deny_unknown_fields` on `FilterArgs`, `PanesArgs` and `OverlaysArgs` as well, since the setter tools are meant to report what they could not do.
