### Findings

1. **crates/core/src/scan.rs:547-549, 627-641 (and crates/native/src/hold.rs:5-9)**: The worst-case bound changed, but the comments still describe the old one. `MAX_PAUSE`'s comment says a stuck or leaked pause "slows a scan to one file per worker per `MAX_PAUSE` at worst". `wait_unpaused` restarts its clock on every call, though. Pass 2 now calls it at up to 6-7 stage boundaries per file (after the read, after the decode, after YuNet, after the mesh, before the score, before the full read, after the full read), and `acquire` adds two more waits. So a pause that stays held costs each worker up to about 8 s per file in pass 2, not 1 s. This matters more now that the native app holds the pause until a paint, not just across a synchronous read. If a load finishes while no frame gets painted (for example, the window is minimized or occluded and GPUI skips the draw), `PaintHold` keeps the pause until the next paint. Pass 2 then crawls at about 3 workers / 8 s per file, and pass 1 at one file per worker per second, during the time the user expects the scan to make progress in the background. Fix options: (a) give the whole file one pause budget, not one per stage. For example, store the instant pass 2 first saw the pause in the `PASS_SLOTS` thread-local, have `wait_unpaused` measure against that, and reset it once a wait sees no pause, as `acquire`'s `paused_since` does. (b) Release `PaintHold` on a short timeout if no paint follows. Whichever you choose, make the `MAX_PAUSE` comment, `wait_unpaused`'s comment, `hold.rs`'s "only slows the scan", and the `native-app.md` paragraph state the real worst case.
2. **docs/agents/native-app.md:183-197**: The new section only describes how the longer hold affects pass 2. In the native app, the hold now also blocks pass 1's `acquire` from the read through the decode, orient and paint, where before it only covered `read_preview`. Paging during pass 1 was not re-measured on this branch. That earlier measurement is in the "During pass 1 the preview reads what the scan already read" section, and it assumed a pause only around the read. Add a sentence saying the longer pause applies to pass 1's reads too and that its effect on pass 1's throughput was not measured (or measure it). Otherwise the next reader will assume pass 1 behaves as it did before.

### Fixed

The `MAX_PAUSE`, `wait_unpaused`, `hold.rs` and `native-app.md` text now state the real worst case (about 3 s per pass 2 file, 1 s per pass 1 file).
2. Added to `native-app.md` that the longer hold also blocks pass 1's `acquire` and that its throughput effect was not measured.
