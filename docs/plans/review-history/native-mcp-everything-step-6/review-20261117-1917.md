## Round 1

**Reviewed commit**: `345463b20c770b72d2245f36a754088fae814ceb` feat(native): add MCP tools for Rewrite Sidecars, Delete Sidecars, Sequence JPEG Timestamps and cancel_operation

STATUS: NEEDS_FIX

### Findings

1. **crates/native/src/companion.rs:899 (`folder_operation`)**: A `rewrite_sidecars` / `delete_sidecars` call without `confirm` goes through `folder_op` → `request_sidecars` → `gate_request`, which discards whatever the gate holds. If the user confirmed a Move to Trash, an undo / redo of one, or a folder rename during a scan (the gate holds it as `HeldOp::Run` / `Undo` / `Redo` / `Rename`), a mere preview request from an MCP client silently drops the user's confirmed operation. It is only recorded as `failed: dropped: a later request replaced it`. This is the case `HELD_REFUSAL` exists for ("a client's confirmed run or undo would replace the user's held one"), and `trash_photos` and the trash undo / redo apply it. The learnings say `HELD_REFUSAL` is not applied because "these runs never enter the gate". That holds for the confirm, but not for the sidecar *start*. Fix: refuse a sidecar start (`FolderOp::Sidecars`, no `confirm`) with `HELD_REFUSAL` while `view.held` (the sequence start does not touch the gate and can stay as is), and add a test next to the existing `HELD_REFUSAL` ones.

2. **crates/native/src/folderops.rs:653 (`run_sequence`) / crates/native/src/main.rs:4696 (`operation_of`)**: A sequencing run can only be reported through the single `running_op` slot, so it goes untracked when it overlaps a trash run. Two cases reach this. (a) The user starts Sequence JPEG Timestamps from the tree menu while an MCP-confirmed trash run is in flight. `start_sequence` only checks `trash.busy()`, which stays false for an `own == false` run. The comment "A trash run an MCP client confirmed keeps its own label" covers this case. (b) An MCP-confirmed sequence run starts while a trash run is held (the folder confirm does not check `view.held`), and the gate later drains it: `run_trash` then overwrites `running_op`. In both cases the trash run's end takes `running_op`. From then until the sequence ends, `operation_of` falls through to `last_op` (the trash run, `finished`), `Status::idle()` is true, and `wait_for_idle` returns while files are still being written. When the sequence ends, `sequence_ran` sees `running_op != Some(sequence::LABEL)` and never records it, so `get_status` never reports its result. Fix: derive the sequencing state from the flow instead of the shared slot. For example, in `operation_of`, report `Running` with `sequence_progress()` whenever `folderops.sequence_running()` and `running_op` is not set. In `sequence_ran`, record the result whenever the run was the flow's own, not only when `running_op` still names it.

3. **crates/native/src/main.rs:5227 / crates/native/src/folderops.rs:389 (`run_confirmed`)**: The confirm clears `mcp_pending` before `run_confirmed` runs. A sidecar run that `run_sidecars` refuses because a listing or scan is under way (any folder open or watcher re-listing in between) therefore loses the client's preview, and the reply is the bare `SCAN_RUNNING` text ("a scan is running; wait for it to finish"). That message suggests the same id can be confirmed again after waiting, but the retry fails with "no preview of … has id N; preview again". A trash confirm in the same situation is held for the scan instead. Fix: check the listing / scan condition before consuming the `Pending` (e.g. expose `resync.busy() || gate.in_flight()` in `View` and refuse in `folder_operation` with a message pointing to `wait_for_idle` and a retry of the same id), so the `Pending` survives the refusal. Alternatively, keep the `SCAN_RUNNING` refusal but add "preview again" to the MCP reply. Either way, update the `delete_sidecars` tool description and `docs/agents/native-app.md` to say which one applies.

### Fixed

1. Sidecar start refused with HELD_REFUSAL while the gate holds an operation (test added).
2. operation_of reads the sequencing run from the flow; sequence_ran records the result regardless of running_op.
3. The Pending is put back on the SCAN_RUNNING refusal and the reply points to wait_for_idle and the same id; docs updated.
