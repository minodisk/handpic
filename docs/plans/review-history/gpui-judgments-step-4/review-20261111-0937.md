## Round 1

**Reviewed commit**: `16e23c36a1aa99d9f4d817042f9612e1a2cbf1eb` feat(native): write the judgments to the index and the sidecars

STATUS: NEEDS_FIX

### Findings

1. **crates/native/src/main.rs:832-875 (`Riffle::store`)**: Each judgment key starts its own `cx.background_spawn` task, and GPUI's background executor is a thread pool, so two keys on the same file can reach `judgment::store` in either order. Each task carries a complete `after` state (rating, flag and label together), so whichever task runs last decides the final row and the final `Writer::set`. Example: with Auto-advance off, `3` then `p` sends `{3, None}` then `{3, Pick}`. If the second task takes the index `Mutex` first, the row and the `.xmp` end at `{3, None}`, the pick is lost from the files, and the view still shows the pick. This is more likely while pass 1 or pass 2 is writing rows, because both tasks then wait on `index::lock` and `std::sync::Mutex` does not hand the lock out in FIFO order. The Tauri side gets its ordering from IPC; nothing here gives the same guarantee. Fix: run the stores in key order. One option is to send `(dir, path, after, label_known, format, names, before)` into one channel drained by a single background task or thread. Another is to chain each store onto the previous store's `Task`. Either way, a failure still has to come back to the view to revert. Add a test that sends two stores for one path back to back while another thread holds the index lock, and check that the row and the sidecar end at the second state.

## Round 2

**Reviewed commit**: `11135db4eefc2c6d532c5464292ff3bd7c2879ab` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 1 / dismissal accepted 0 / re-raised 0

### Findings

1. **crates/native/src/main.rs:351-355 (`App::on_app_quit`) with crates/native/src/judgment.rs (`Queue`)**: The quit hook drains only the `Writer`. The new `judgment-store` thread runs before the writer: it writes the ratings row and only then calls `Writer::set`. A key pressed just before quit can therefore still be queued, or blocked on `index::lock` while pass 1 / pass 2 holds it, when `writer.flush` returns. In that case the process exits with neither the row nor the sidecar written, and the next open's dirty-row recovery cannot save it because the row was never marked. The single thread also makes a backlog more likely than the old pool did, since every store now waits behind the one before it. This defeats the point of the quit drain ("the writer drained in App::on_app_quit"). Fix: give the quit hook a handle to the queue (for example, keep the `mpsc::Sender` in an `Arc` shared with the hook), and add a `Queue::drain(timeout)` that sends a barrier job and waits for its reply within the timeout. Call it before `writer.flush(DRAIN_TIMEOUT)` and log the result next to `drained=`. Add a test that holds the index lock, submits a store, releases the lock, calls `drain` and then `writer.flush`, and checks that the row and the `.xmp` hold the state.
