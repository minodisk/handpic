### Findings

1. **crates/native/src/main.rs:1688-1718 (`restored`), with `set_entries` (main.rs:2207-2220)**: after an undo in the open folder, the restored files get added to `all` straight away, but their judgments do not come back with them. The re-listing that followed the original run went through `Scan::prepare`, whose `Index::reconcile` dropped the moved files' rows. `entries_of` then re-read the entries without them, and `set_entries` replaced `self.judgments` and `self.seen` with that map. So a second `Ctrl+Z` pressed before the post-restore re-listing lands has a problem. Take the case where it reaches the judgment batch under the trash run, e.g. the reject that led to the trash, and is pressed before the re-listing's sidecar pass reads the restored sidecar back:
   - `listed` passes, because the path is in `all`.
   - `current` falls back to `State::default()`.
   - So `history::step` pushes a redo entry holding the default state instead of the file's real judgment. A later redo then clears the judgment instead of re-applying it.
   - `label_known` is computed against a `seen` that lacks the path.
   - The strip also shows the restored cells with no marks until the re-listing ends.

   The Tauri app avoids this on purpose: its `trashed` keeps `ratings` / `flags` / `labels` for the moved paths "for an undo landing before the rescan". The new native-app.md rule ("so a second undo already reaches their judgments") and manual check 3 in learnings.md assume the same, but the native code does not deliver it.

   Suggested fix: in `trashed`, for a `Mode::Trash` run, stash the moved paths' `judgments` entries and `seen` membership in a field keyed by path. In `restored`, for the `back` paths, put them back into `self.judgments` and `self.seen` and call `strip.set_judgment` after the `refilter`. Alternatively, have `set_entries` keep the old state for paths missing from the fresh map. Add a test if the stash logic is pulled into a pure helper.
