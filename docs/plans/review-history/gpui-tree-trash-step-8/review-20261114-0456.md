## Round 1

**Reviewed commit**: `9b6b14fbb7ac79fa5f228c4de8a4374e89f424c1` feat(native): undo and redo a move to the Trash

STATUS: NEEDS_FIX

### Findings

1. **crates/native/src/main.rs:1688-1718 (`restored`), with `set_entries` (main.rs:2207-2220)**: after an undo in the open folder, the restored files get added to `all` straight away, but their judgments do not come back with them. The re-listing that followed the original run went through `Scan::prepare`, whose `Index::reconcile` dropped the moved files' rows. `entries_of` then re-read the entries without them, and `set_entries` replaced `self.judgments` and `self.seen` with that map. So a second `Ctrl+Z` pressed before the post-restore re-listing lands has a problem. Take the case where it reaches the judgment batch under the trash run, e.g. the reject that led to the trash, and is pressed before the re-listing's sidecar pass reads the restored sidecar back:
   - `listed` passes, because the path is in `all`.
   - `current` falls back to `State::default()`.
   - So `history::step` pushes a redo entry holding the default state instead of the file's real judgment. A later redo then clears the judgment instead of re-applying it.
   - `label_known` is computed against a `seen` that lacks the path.
   - The strip also shows the restored cells with no marks until the re-listing ends.

   The Tauri app avoids this on purpose: its `trashed` keeps `ratings` / `flags` / `labels` for the moved paths "for an undo landing before the rescan". The new native-app.md rule ("so a second undo already reaches their judgments") and manual check 3 in learnings.md assume the same, but the native code does not deliver it.

   Suggested fix: in `trashed`, for a `Mode::Trash` run, stash the moved paths' `judgments` entries and `seen` membership in a field keyed by path. In `restored`, for the `back` paths, put them back into `self.judgments` and `self.seen` and call `strip.set_judgment` after the `refilter`. Alternatively, have `set_entries` keep the old state for paths missing from the fresh map. Add a test if the stash logic is pulled into a pure helper.

## Round 2

**Reviewed commit**: `e1ac24268528d6750a3973742b86d783d3cccbfe` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 0 / dismissal accepted 0 / re-raised 1

### Findings

1. **crates/native/src/main.rs:1250-1263 (`restored`), with `set_entries` (main.rs:2231-2243) and `entries_of` (main.rs:256)**: this only partly fixes Round 1 item 1 (repeat). `restored` now takes the stashed state out of `trashed_state` (`remove`) and lays it over `judgments` / `seen`. But it then calls `relist` straight away. That carry listing's `set_entries` resets `self.seen` from the fresh map and replaces `self.judgments` with it, keeping only `touched` paths.
   - The fresh map comes from `Index::entries`, which selects `FROM files LEFT JOIN ratings`. The first trash's re-listing reconciled away the restored files' `files` rows, and a restored file gets its row back only when pass 1 extracts it. So the map lacks those files until pass 1's `Done` triggers `read_entries`.
   - Between the post-restore listing landing and pass 1's `Done`, the restored files lose their judgment and their `seen` membership again, and their strip cells go unmarked. The stash is already gone, so nothing brings them back.
   - A judgment `Ctrl+Z` is not gated on the scan: `step` only routes trash entries through `step_trash`. Pressed in that window, it hits exactly the Round 1 failure: `current` gives `State::default()` for the redo entry, and `label_known` misses `seen`. A large restored run makes the window longer.

   Suggested fix: keep the stash in force until a fresh map actually has the path. For example, in `set_entries`, for a listed path missing from the fresh map, take its state from `trashed_state` (or keep the old `self.judgments` / `seen` value for it). Drop a `trashed_state` entry only once `entries_of` returns that path. Pull the merge into a pure helper with a test covering "restored path absent from the fresh entries keeps its stashed state and `seen`".
2. **crates/native/src/main.rs:1125-1130 (`trashed`)**: entries in `trashed_state` are removed only when an undo restores the path while its folder is open. So an undo run from another folder leaves its paths stashed for the rest of the session. So does a trash entry that drops off the bounded history or is removed by `remove_trash`. A later restore into the open folder then lays that old state over the path if nothing newer replaced it. Suggested fix: drop the paths of a trash entry from `trashed_state` when that entry leaves the undo/redo histories, or when an undo restores them, whichever folder is open. Alternatively, key the stash by the entry's `run_id`.

### Dismissed

- Item 2 (partly): the stash is now dropped when an undo restores its paths from another folder, which covers the cross-folder case. Dropping it when an entry falls off the bounded history or is removed by `remove_trash` is not done: `carry_stash` only lays a stash entry over a path that is currently listed and absent from the fresh entries, so a stale entry is inert unless that same file reappears in the open folder, in which case the last judgment it held is the right one to show. A later trash of the path overwrites the entry. The added tracking through `History` would cost more than this residual case is worth.
