### Findings

1. **[crates/app/src/main.rs:5859 (`tasks`)]**: A folder rename and a `Rename by Capture Date…` split show a task only while they wait. They have no task once they run. The gate's held rename gets the folder slot's dim "waiting" indicator (`Sources::held`). When the gate drains and `run_rename` / the date split start, they set `running_op` to `rename::LABEL` / `datefolder::LABEL` and enter the gate's in-flight count. Neither has a `*_progress()` counter, so `Sources::folder` stays `None` and the indicator disappears while the operation is still in flight. The user sees "waiting", then nothing, while the work goes on (`get_status` still reports it as running). The plan's done-when asks for "every running task ... `done` / `total` or indeterminate", and `Amount::Unknown` already exists for this. Add those two runs to the folder slot as `Unknown` tasks: for example a `FolderRun::Rename` / `FolderRun::DateFolder` variant fed when `folderops.renames` has one in flight or the date flow is running. Give them a tip such as `"{label}…"`, and add a unit test for each.
2. **[crates/app/src/uitest.rs:893 (`the_task_list_holds_the_scan_beside_a_held_rename_and_empties_at_the_end`)]**: The test depends on timing. `wait_until("the scan's task beside the held rename", ...)` must catch the scan mid-pass between two polls, but the scan runs on real background threads over three minimal DNGs. When pass 1 and pass 2 finish inside one `run_until_parked` + poll interval, the pending events drain together. The held rename then runs and `tasks.len() == 2` never holds, so the test times out at `WAIT`. `learnings.md` already names this risk. The sibling held-rename test relies only on the synchronously set hold, so it does not have this problem. Make the observation deterministic: hold the scan with its `Paused` handle (`ReadSlots`' pause, the one `PaintHold` holds) before opening the folder and release it after the assertions. Alternatively, record the task list from the view's handling of the first `Progress` event instead of polling for it.

### Fixed

1. Added `Sources::folder_uncounted`, fed from `running_op` being `rename::LABEL` or `datefolder::LABEL`, which gives the folder slot an `Amount::Unknown` task with the tip `"{label}…"`; unit test `an_uncounted_folder_run_is_an_unknown_task_under_its_label` covers both labels.
2. The UI test now holds a `ReadSlots` pause from before the folder opens until after its assertions, so the scan's task is observable deterministically.
