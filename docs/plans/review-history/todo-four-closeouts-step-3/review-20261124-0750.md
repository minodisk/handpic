### Findings

1. **crates/core/src/scan.rs:383**: `score_gray` now runs inside the cue's `guarded` closure, so a panic in the scoring also throws away the cue (`guarded` maps any panic to `Cue::unknown()`). Before this change the score had its own `catch_unwind` in `score()` and a scoring panic could not touch the cue, and the cue's mesh, EAR, pose and `full_eye_sharp` came out the same either way. To keep that isolation, wrap the call in its own guard, e.g. `scored = catch_unwind(AssertUnwindSafe(|| score_gray(..))).ok().and_then(Result::ok);`. A scoring panic then leaves `scored` as `None`, and the caller falls back to `score()`, which fails the same way it did before.
2. **crates/core/src/scan.rs:362-366, 283**: The new `faces: &[Face]` parameter repeats `detection.faces`. The only caller passes `detection.faces.clone()`, and `whole_image_cue` already owns `detection`. Having both lets the two disagree: the test already calls it with `whole(vec![large])` as the detection and `&faces` (three faces) as the score's faces, which no real call can do. Inside the closure, take the score on `&detection.faces` before `detection` is moved into `face_cue_unless`, and remove the parameter. The test's expected score then uses the detection's own faces.
