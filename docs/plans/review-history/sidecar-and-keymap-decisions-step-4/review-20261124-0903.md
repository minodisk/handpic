## Round 1

**Reviewed commit**: `ac81d9b4533b59fffce715305d7a2e437d17e0e0` fix(engine): let a stored shortcut override win over an un-overridden default

STATUS: NEEDS_FIX

### Findings

1. **crates/engine/src/shortcuts.rs:473 (`reset`), :442 (`remove`), :499 (`overrides`)**: An edit made during the session that frees a displaced key does not give that key back to the keyless action, so the in-memory keymap stops matching what reloads. Example: load `{"reject": ["p"]}`, which leaves `pick` with `[]`. Then call `reset("reject")`, or edit `reject` to `["p", "x"]` and remove `p`. Now `p` is free and `reject` is back to its default, but `pick` still has no key. `overrides()` returns `{}` because it skips the empty `pick` and `reject` equals its default. After a relaunch, `pick` gets `p` back. So for the rest of the session `pick` is unbound in `Bindings`, in the Keyboard Shortcuts row and in `get_settings`, even though the saved state says it holds `p`. The invariant `from_overrides(Some(&keymap.overrides())) == keymap` that this step depends on breaks after a single edit. Before this change no action could have zero keys, so `reset` and `remove` never needed to deal with this. Suggested fix: after `reset` and `remove` (the edits that can free a key), give every action with no keys back the default keys that are now free. The simplest version is to re-derive the keymap through `Keymap::from_overrides(Some(&self.overrides()))`. Add an engine test: load `{"reject": ["p"]}`, `reset("reject")`, assert `pick` holds `["p"]`, then check the round trip.

2. **crates/engine/src/shortcuts.rs:320-326**: The `warn` line names the first pending override in action order that asks for the key. That is not always the action the retries give the key to. The learnings claim it is ("which is the one the retries give it to when two want it"), but that claim is wrong. Counterexample: `{"reject": ["p", "0"], "unflag": ["p"], "clear": ["c"]}`. The displacement pass logs `moving "p" from pick to reject`. In the first retain pass, `reject` is not fully free because `clear` still holds `0`, so `unflag` gets `p` outright. `reject` then applies only in part, as `["0"]`, and `p` ends up on `unflag`. A log line that names the wrong action defeats its purpose, which is telling the user where their key went. Suggested fix: log the moves after the retries and the `partial` recompute settle. Keep the displaced `(key, action)` pairs, and at the end name `holder` of each key (or no one). Alternatively, reword the line so it does not claim a destination, for example `removing "p" from pick: the stored shortcut for reject asks for it`. Then correct the bullet in `docs/plans/20261123-sidecar-and-keymap-decisions/learnings.md` to match.

### Fixed

1. `reset` and `remove` now re-derive the keymap from its own overrides (`refill`), so a keyless action gets back its freed default keys; test `an_edit_freeing_a_displaced_key_gives_it_back` added.
2. The warn line no longer names a destination (`removing "p" from pick: a stored shortcut asks for it`); the learnings bullet is corrected.
