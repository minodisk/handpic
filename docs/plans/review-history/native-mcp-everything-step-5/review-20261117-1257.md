## Round 1

**Reviewed commit**: `292ebf281078e66230564fa60dfd73681f0b45a9` feat(native): add trash_photos and the undo / redo of trash runs over MCP

STATUS: NEEDS_FIX

### Findings

1. **[crates/native/src/main.rs:5097 / 5108, crates/native/src/companion.rs:573 / 628]**: An MCP-confirmed `Action::Run` (`request_run`) and an MCP `Action::StepTrash` (`perform` -> `step_trash`) both go through `gate_request`, which first `discard`s whatever the gate already holds. So with a listing or scan under way, an MCP call silently drops an operation the *user* confirmed and the gate is holding: their held `Delete Permanently` / `Move to Trash`, their held `Undo Move to Trash`, or a held folder rename or sidecar operation (only a rename gets a note). None of the companion's checks catch this, because the dialog is already closed once the run is held, `trashing` is still `None`, and `folder_op` does not cover the gate. The user never sees that their decision was replaced by a client's. Fix: add a `held: bool` (from `self.gate.waiting().is_some()`) to `View`. Refuse `trash_photos` with `confirm: true` and `undo` / `redo` whose top is `Top::Trash` while it is set, with a message saying an operation is held for the scan's end. Add unit tests for both refusals.
2. **[crates/native/src/main.rs:2332 (`finished`), main.rs:997 / folderops.rs:1692 (`gate.discard` on an open)]**: When a held MCP run is dropped (a dialog was open when the scan ended, a folder was opened, or a later request replaced it), nothing updates `last_op`. `get_status` goes from `held_for_scan` straight to the *previous* operation's `finished` / `failed`, and `wait_for_idle` returns as if the run had ended. A client that follows the documented `wait_for_idle` -> `get_status` pattern cannot tell that its confirmed run never happened, and may report that the photos were moved. Fix: when a held `Run` / `Undo` / `Redo` is dropped, record it as `OpState::Failed` with a message such as "dropped: <reason>" (e.g., a `record_op`-like helper called from these drop sites). Document the new state in `get_status`'s description.
3. **[crates/native/src/main.rs:2411, crates/native/src/main.rs (`mcp_pending`)]**: The `Pending` preview lives until it is confirmed or another preview replaces it. Turning `mcpAllowDestructive` off does not invalidate it, and neither does opening another folder and coming back. If the user revokes the switch and later turns it on again, a client can confirm a preview made under the earlier grant without previewing again. Confirming re-checks the switch, the folder and that the photos are shown, but not that the grant is the same one. Revoking should invalidate outstanding confirmations. Fix: set `self.mcp_pending = None` where `Change::McpAllowDestructive(false)` is applied (line 2411), and on every folder open.
4. **[crates/backend/src/mcp.rs:816-818]**: The new `trash` function was inserted between `idle_wait`'s doc comment and `idle_wait`. `/// How long \`wait_for_idle\` waits for \`timeout_ms\`.` now precedes `/// \`trash_photos\`' request: the fields given.` on `fn trash`, so `trash` has two unrelated doc lines and `idle_wait` has none. Fix: move `fn trash` (with its own doc line) above that comment, or below `idle_wait`.
