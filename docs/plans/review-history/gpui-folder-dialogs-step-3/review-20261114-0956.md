### Findings

1. **[crates/native/src/main.rs:2378 (the `settingsmodal::OPEN_KEY` arm of `key_down`) / crates/native/src/folderops.rs:521 (`sidecars_previewed`)]**: The settings modal can open while a folder flow is busy. Between `start_sidecars` and the preview's return (`Phase::Previewing`, which includes `stores.drain` and `writer.flush` with `DRAIN_TIMEOUT` and can take a noticeable time), `self.folderops.dialog_open()` is false, so `Ctrl+,` gets through to `view.open(...)`. When the preview comes back, `sidecars_previewed` opens the folder dialog anyway. The result is the settings modal and the folder dialog open together. `key_down` returns early while the settings are open, so the folder dialog can be used only with the mouse. Also, if the sidecar format is changed in the settings meanwhile, `run_sidecars` takes `self.settings.format` at run time. It would then rewrite or delete a different format from the one the dialog's total line named (`Rewrite the XMP sidecars of …`). The Tauri app prevents this: its settings-open handler (`main.ts`, the listener that calls `settings.open()`) returns early while `sidecarFlow.busy` (and `trashFlow.busy` and the other flows). Suggested fix: refuse the `OPEN_KEY` arm while `self.folderops.busy()`, matching the Tauri guard (`self.trash.busy()` is already covered by the earlier key routing). Alternatively, or as well, end the flow in `sidecars_previewed` when the settings are open. Add the case to the hand-check list in `learnings.md`.
