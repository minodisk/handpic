### Findings

1. **crates/cli/src/main.rs:417-419**: The new `COPYBENCH_USAGE` const and `copybench` were inserted between `scan_dir`'s doc comment (`/// Extract a whole folder in parallel, with no database: the folder scan throughput benchmark.`) and `scan_dir`. That comment now documents `COPYBENCH_USAGE`, and `scan_dir` has no doc comment. Move the const and `copybench` above that comment (or below `scan_dir`) so the comment stays on `scan_dir`.
2. **crates/core/src/copy.rs:300-308**: `Writer::fail` can run twice for the same job, and each run calls `end`, which adds `sizes[job]` to `base` again and increments `files_done` again. This happens when the writer fails a job first (a `create` error on `Begin` or a `write` error on a chunk) and the reader then sends its own `Msg::Fail(job, "read: ...")` because a `fill` it started before `abandoned` was set hits an I/O error. Then `files_done` goes above `files_total`, and `bytes_done` runs ahead (it is only clamped at the total). Both failures together are unlikely, but the dialog's `importing N / M` in Step 4 depends on these counts. Make `fail` idempotent per job: return early if `self.results[job]` is already `Outcome::Failed`. Better still, keep the later error out of `results` too, since the first error is the cause.
