## Round 1

**Reviewed commit**: `e70f9592967e6997792bc7a02fd8847dc9b7d521` feat(app): add Delete Permanently to the strip's menu (trash-over-scan Step 5)

STATUS: NEEDS_FIX

### Findings

1. **[crates/app/ui/src/main.ts:1085]**: A double-click on the menu item can confirm the delete. `runTrash` only rejects `event.detail === 0`, but the menu item acts on its first `click` (`showMenu`) and the dialog is up before the second click of a double-click lands. `#trash-dialog` is a centered full-window overlay, and `canvas`'s `contextmenu` listener opens this same menu at the cursor over the viewer. So after a right-click in the upper middle of the viewer, the last item (`Delete Permanently…`) can sit right where `#trash-run` appears. The second click then reaches the run button as a real mouse click with `detail` 2, and the files are destroyed with no deliberate click on the dialog. Require `event.detail !== 1` to ignore the click, which also keeps the keyboard case (`detail` 0). A later deliberate single click still works. Moving the test into a pure `trash.ts` helper next to `swallowedByDelete` would give this guard a vitest case; it has none today because it sits inline in `main.ts`. Update `docs/agents/tauri-app.md` to match.

2. **[crates/app/src/trash.rs:357]**: A delete can destroy a file that was not confirmed: the `FOO.xmp` a kept RAW still uses. `delete_for_good` reuses `groups_of`, so deleting `FOO.ARW` also removes the `FOO.xmp` shared with an unselected `FOO.DNG`. That wipes the kept file's judgment, and any Lightroom edits in that XMP, with no way back. The dialog says only "and their sidecars", and the only warning is the README's "not supported" note. That note was acceptable for a move, which Undo restores, but it is not enough for this operation. Keep the `.xmp` out of the group when another RAW with the same stem in `listing.files` is not among `paths` (`.dop` is per file and unaffected), and add a test to `trash.rs`. If the intended behavior stays as it is, the dialog must at least name the shared sidecar before the click, as the README alone does not reach the person confirming.

3. **[crates/app/ui/src/main.ts:1130]**: `trashed()` leaves the deleted files' judgment batches in `history` and `redoable`. A move protects them with the `kind: "trash"` entry above them; a delete pushes nothing. This is the flow the usage docs recommend (reject, filter, select all, delete), and two things go wrong:
   - After the rescan, `step` pops the batch, filters every path out and returns, so an Undo is consumed silently, with no status line.
   - Until the rescan's listing lands, `allFiles` still holds the paths, so an Undo judges a gone file and can mint an orphan sidecar next to it. That is the case `foldersidecars::targets` explicitly avoids ("no sidecar is minted next to a file that is gone").

   The learnings defer this, but the PR introduces it and the fix is small, so it belongs in this step. When `mode === "delete"`, drop `summary.moved` from every judgment batch of both stacks and remove the batches left empty, with a vitest case if the pruning is pure.

4. **[docs/agents/tauri-app.md:1921]**: The two new bullets were inserted in the middle of the existing `trashing !== null` bullet. Its last sentences ("Only the invoke's own `.then` / `.catch` clear the flag, not `done()`, ... A held trash is still replaced by a later request as before.") now read as a continuation of the `trash-dialog` bullet, where they make no sense. Move lines 1905–1920 below line 1923, so the `trashing` bullet stays whole.

### Fixed

1. `runTrash` now confirms a delete only for `detail === 1` (`confirmsDelete` in `trash.ts`, with a vitest case); `docs/agents/tauri-app.md` updated.
2. `delete_for_good` takes the listing's `files` and keeps a `.xmp` shared by stem with a RAW outside the selection; test `a_delete_keeps_an_xmp_a_kept_raw_shares`; dialog text, both READMEs and the docs updated.
3. `trashed()` drops `summary.moved` from the judgment batches of `history` and `redoable` after a delete (`withoutPaths` / `isEmptyBatch` in `undo.ts`, with a vitest case); the matching deferred item was removed from `learnings.md`.
4. The `trashing` bullet in `docs/agents/tauri-app.md` is whole again; the two new bullets follow it.

## Round 2

**Reviewed commit**: `1241732eee1c987f03740dec2bf9719b7a1a6848` fix: address local review round 1 findings

**Previous feedback**: addressed 4 / dismissal accepted 0 / re-raised 0

### Findings

1. **[crates/app/src/trash.rs:372]**: The Round 1 item 2 fix covers a `.xmp` shared with a RAW outside the selection, but not one shared by two selected RAWs. `sidecars_of` puts `a.xmp` in the group of both `a.ARW` and `a.DNG`, and `run` treats each group on its own. Two things go wrong:
   - A failed RAW loses its sidecar with no way back. With both selected and `a.ARW` locked, `a.DNG` goes and takes `a.xmp` with it, while `a.ARW` stays. That is the data loss Round 1 fixed, and it breaks the plan's rule and `usage.md`'s promise that a file that could not be deleted "stays in the folder with its sidecars".
   - When both go, the second group's `remove_file(a.xmp)` hits NotFound, so a fully successful delete reads `Deleted 2 files, 1 failed` and adds a sticky `could not delete` error. `a_delete_keeps_an_xmp_a_kept_raw_shares` does not cover this case.

   Fix: in `delete_for_good`, take a `.xmp` shared by several groups out of those groups, and after `run` remove it (through `remover`, reporting a failure) only when every RAW sharing its stem is in `summary.moved`. Add tests for both cases. While there, build `chosen` from `groups` rather than `paths`: a refused foreign `other/a.DNG` currently counts as chosen and would stop the kept `dir/a.DNG` from protecting `a.xmp`. The frontend never sends such a path, but `delete_for_good` is the last check before an irreversible removal.

2. **[docs/plans/20261106-trash-over-scan/plan.md:401]**: Step 5 is ticked, but the Progress section has no `Step 5 complete` entry. The plan's `pr-rules` require both in the implementation PR, and Steps 1 to 4 each have one. Add `- (2026-11-07) Step 5 complete`.

### Fixed

1. `delete_for_good` takes a `.xmp` shared by several selected RAWs out of their groups and removes it after `run`, through `remover`, only when every RAW sharing it went (a failure is reported); `chosen` is built from `groups`, so a refused foreign path no longer protects nothing or stands for a kept RAW. Tests added in `trash.rs` for both shared-xmp cases and the foreign same-name case.
2. Added `- (2026-11-07) Step 5 complete` to the plan's Progress section.
