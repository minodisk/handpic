## Round 1

**Reviewed commit**: `ca84cd4947589673d2c8175250c3e1d4a2e3836b` fix(core): rename the import's copy into place without replacing

STATUS: NEEDS_FIX

### Findings

1. **[crates/core/src/copy.rs:452-462 (`verbatim`)]**: On Windows every rename now depends on `fs::canonicalize` of the destination folder succeeding. `canonicalize` opens the folder and calls `GetFinalPathNameByHandleW`, and that call fails with "Incorrect function (os error 1)" on some volumes where a plain rename works: ImDisk / other RAM disks, some Dokan / WinFsp FUSE mounts, and WebDAV redirector drives. std's `fs::rename` never had this dependency, because its long-path conversion (`maybe_verbatim`) uses `GetFullPathNameW`, which needs no handle. So an import into such a destination used to succeed and now fails every job with `rename: ...`. That is a regression the long-path test does not catch. Suggested fix: build the verbatim form the way std does, with `std::path::absolute(path)` (`GetFullPathNameW`) and the `\\?\` / `\\?\UNC\` prefix added only when the result is not already verbatim. A smaller alternative is to fall back to the path as given when `canonicalize` fails. Either option also drops the two extra handle opens per file that `canonicalize` costs.
2. **[crates/core/src/copy.rs:381, 409, 440 (the three `unsafe` calls)]**: The crate's other `unsafe` FFI calls each carry a `// SAFETY:` comment (`scan.rs:1082`, `1097`, `1101`, `1312`, `1326`). The new `renameat2` syscall, `renamex_np` and `MoveFileExW` calls have none. Add one to each, e.g. "both pointers are NUL-terminated strings that outlive the call".
