## Round 1

**Reviewed commit**: `969ee7ed079e46d423906ceaa0620308b3a2027c` fix(engine): report an ongoing burst of folder changes every maximum wait

STATUS: NEEDS_FIX

### Findings

1. **[crates/engine/src/watch.rs:367-401]**: `an_ongoing_burst_is_reported_every_max_wait` never runs `run`'s own logic. It rebuilds the loop in its `report_due` closure and only exercises `burst`. The new part of `run` that actually stops a steady stream from starving the report is the `pending.take_if(|burst| burst.deadline <= now)` emit in the `Ok(dir)` arm, which has to come before `burst(pending.take(), ..)`. With events every 100 ms, `recv_timeout` keeps returning `Ok` and never `Timeout`, so that line is the only thing that reports. If it is dropped or reordered, the test still passes, because the closure carries its own copy of the check. Suggested fix: move the arm's body into one pure function, for example `fn step(pending: Option<Burst>, dir: String, now: Instant) -> (Option<String>, Burst)` (the due folder to emit, then the new pending burst). Have `run` call it and have the test drive `step` instead of a hand-copied closure, so the test covers the code that ships.
2. **[crates/engine/src/watch.rs:211-214]**: `burst`'s doc says that when another folder arrives "its pending report is dropped". `run` now emits the old folder's report first when it is already due, so it is not always dropped. That is harmless, because `Handpic::changed` ignores a `dir` other than the open one. Suggested fix: make the comment match the behavior (an overdue report is still sent, and the app ignores it), or have the `take_if` emit only when `burst.dir == dir`.

### Findings

1. **[docs/agents/app.md:1648]**: The new `import_folder` paragraph says the watcher's reports are "at least `MAX_WAIT` apart". That bound points the wrong way. `burst` gives an upper bound: during a burst a report is due no later than `MAX_WAIT` after its first event. It gives no lower bound. When renames land more than `DEBOUNCE` apart, each one is reported `DEBOUNCE` after it, so reports can come about 0.5 s apart. That happens with large RAWs on a slow source such as a card reader, or with any gap in the copy. The same file already says it the right way at line 1890 ("at least every `MAX_WAIT`"). Suggested fix: say "at most `MAX_WAIT` apart while copies keep landing", or say "every `MAX_WAIT` while the renames come faster than `DEBOUNCE`", to match the rule at lines 1884-1887.
