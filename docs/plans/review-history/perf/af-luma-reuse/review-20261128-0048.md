## Round 1

**Reviewed commit**: `ca193ba454b7fd4825b1ab6fb9aeac6d64976d37` perf(core): score a trusted-AF file on the luma of the cue's decode

STATUS: NEEDS_FIX

### Findings

1. **crates/core/src/scan.rs:316-325**: The AF arm now binds `rgb` from `af_cue` and keeps it alive to the end of the arm, which means the full-size RGB buffer is held during `af_gate_count`'s second decode (`faces::decode_gate`) and its YuNet search. Before this change it was dropped right away (`let (cue, _) = ...`). The AF path covers most files. On the 1616x1080 ARW previews that adds about 5 MB per worker, and on the 4416x2944 RAF previews this change also covers it adds about 39 MB, held for the length of the gate search. This raises each pass-2 worker's peak memory for no benefit. Drop the buffer once it is scored, before the gate search. For example, compute `scored` and then call `drop(rgb);` ahead of `yield_to_pause`, or move the decode and the score into a block that returns `(cue, scored)`.
2. **docs/humans/performance.md:974-975**: "a file whose RGB decode fails still scores through that decode" is ambiguous. The nearest decode in the sentence is the RGB decode that just failed, but the code (`score`, `score_preview`) falls back to the file's own grayscale decode. The Japanese text (`以前どおり自前のデコードで`) and `shared-crates.md` ("still scores through its own decode") both say it unambiguously. Reword it to "still scores on a grayscale decode of its own, as before" (the `.ja.md` already matches this meaning).
