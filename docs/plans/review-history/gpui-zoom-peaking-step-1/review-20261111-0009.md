## Round 1

**Reviewed commit**: `88310654e22dc2f7081fa2fb7e144963a0d076c6` feat(native): add the 1:1 view on z

STATUS: NEEDS_FIX

### Findings

1. **crates/native/src/main.rs:498 (`opened` calls `self.zoom_page(cx)` on a carry re-listing too)**: A watcher resync (`relist` → `list(.., carry = true)` → `opened`) calls `zoom_page` even when `carry` keeps the same file current. `Zoom::page` bumps `seq` and releases the held crop. The new `seq` also hides the placeholder, because `Zoom::preview` only answers for the `seq` that `shown` recorded, and the preview is re-read for the new pager. So while zoomed, every change the folder watcher reports (an external sidecar write, a file copied in) leaves the canvas blank until the preview read returns. Then the scaled placeholder shows until a new crop arrives, all on the file the user was already inspecting. The fit view does not flicker this way, because it keeps `self.image` until the new one replaces it. The Tauri app also keeps the zoomed crop on a re-listing that leaves the current file in place: `mustReshow` is false, so there is no `seq += 1` and no `show()`. Suggested fix: in `opened`, call `zoom_page` only when `!carry` or when `carry` changed the current file. One way is to compare `path_strings(&self.files)[was]` with `paths[current]` before `self.files = shown`, as `carry` already does for the dwell. Add a `Zoom` unit test or a note in `learnings.md` for the case. The plan's "a listing bump drops a crop read for the previous listing" is about an in-flight result for another file. A crop of the same file and viewport from the previous listing is still correct to show.

### Addressed

1. Fixed: `opened` skips `zoom_page` on a carry re-listing that leaves the same file current, so the held crop and `seq` stay. A note was added to `learnings.md`.
