### Findings

1. **[crates/app/ui/src/main.ts:1725, main.ts:1742]**: `finishImport` does not wait for the `openDirectory` that `runImport` started, so an `import-done` that lands while that open is in flight goes wrong in two ways. (a) `openDirectory`'s `.then` later runs `errors.clear()` and `show()` / `setStatus()` (main.ts:4159 onward), which wipes the failures `finishImport` just put in the sticky `errors` list and the done status line. On the `done !== null` branch of `runImport` this is deterministic, because `finishImport(done)` runs synchronously right after `openDirectory` is called and always before it resolves; a failed file of that run is then no longer shown in the UI. (b) `openDir` is still the previous folder at that moment, so the `opensTarget(openDir, payload.folders, ...)` check added for the "file landed between the listing and the watch" gap is false and `resync("import")` is skipped. A small import that finishes during the open, where `list_arw` ran before the last file landed, leaves the strip short with no further trigger, which is exactly the gap this check is meant to close. Both come from the same ordering problem: keep the promise of the import's open and run the body of `finishImport` after it settles (for example `const opening = openDirectory(...).catch(...)` held in a variable that `finishImport` chains on, with `importFlow.done` still deciding synchronously). Add a test at the level where the ordering can be exercised, or extract the decision into `ImportFlow` so it can be.

2. **[crates/app/ui/src/main.ts:440 `holdRename`, used by `renameFolder` and `renameFile`]**: the tree's inline folder rename and the strip's file rename are not gated on `importFlow.busy`. Up to Step 4 the modal dialog made them unreachable during a run; now that it steps aside they are reachable, and they are held only until the scan's end, so they execute mid-copy. `copy.rs` creates each `<dst>.riffle-tmp` with `File::create` and no `create_dir_all`, and `prepare` makes the folders only once, so renaming a date folder that is still to be filled (or its year parent, or a source folder on the card) makes every remaining file of it fail, and `import-done`'s `folders` then names a path that no longer exists. Renaming a RAW that just landed moves its sidecars so far, and sidecars still to come land under the old name as orphans. `renameByDateIn`, which does the same thing to a folder, already refuses on `importFlow.busy`, and `learnings.md` says the mutating flows refuse during a run; rename was missed. Refuse there too: check `importFlow.busy` inside the `run` closure of `holdRename` (a held rename can outlive the check at confirm time, as `trashFilesIn` handles) and revert the pending name with a status note, plus at `folders.startRename` / the strip's rename entry if an edit that cannot be committed should not open at all. Record it in `learnings.md`.

3. **[crates/app/src/import.rs:807]**: `prepare(&plan)` runs `fs::create_dir_all` for every date folder directly in the `async` command, outside `spawn_blocking`, and inside `begin`'s closure, so with the `Imports` mutex held. `docs/agents/tauri-app.md` requires an `async` command doing blocking IO to wrap it in `spawn_blocking`, and the "small local file" exception does not apply: the destination root is user-chosen and can be a NAS or a sleeping disk, where this stalls an async runtime worker, and `import_cancel` blocks on the same lock meanwhile. `import_preview` in this file already follows the rule (import.rs:538). Keep "a refused run creates nothing" by moving `prepare` onto the blocking task: claim the run in `begin`, have the `spawn_blocking` body run `prepare`, hand `folders` back over a `tauri::async_runtime::channel(1)` (the pattern the guide names), then copy, and `await` the channel in `import_run` after `begin` returns, so no lock is held across the IO.
