### Findings

1. **[crates/app/src/migrate.rs:60-70]**: The "newest first" guarantee stated in the `LEGACY_IDENTIFIERS` doc comment only holds when the `com.minodisk.handpic` merge completes. If one of its files fails to move (e.g. a file held open, which the plan calls out), the loop still goes on to merge `com.minodisk.riffle`, so Riffle's copy of that file can land in `dev.minodisk.handpic` first. On the next launch the newer Handpic copy then meets an existing destination and `move_file` deletes it (`fs::remove_file(source)`), so the older Riffle data wins silently. That is the exact inversion the ordering is supposed to prevent. Fix: stop at the first legacy identifier that is not fully moved (`if !all_moved { complete = false; break; }`, or skip later entries once `complete` is false). A partial run already keeps the app from starting and resumes on the next launch, so nothing is lost by stopping early. Add a temp-dir test that injects a failing `rename` for one Handpic file (on both the rename and the copy fallback, e.g. a source that is a directory where the destination expects a file, or a rename hook plus a read-only source) and checks that the Riffle folder is left untouched.
2. **[docs/plans/20261113-identifier-dev-minodisk/plan.md:82]**: Step 1 is ticked, but `## Progress` is empty. The plan's own `<pr-rules>` require the implementation PR to include "the plan.md update (marking the step done + the Progress entry)". Add `- (2026-11-13) Step 1 complete`, with a note that the first-launch manual check is pending (see `learnings.md`), following the archived plans' format.
