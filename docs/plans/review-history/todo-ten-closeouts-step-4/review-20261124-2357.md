### Findings

1. **[crates/app/src/main.rs:4639-4645 (`prefetch_crop`) / crates/app/src/prefetch.rs:49-57 (`Heading::to`)]**: With `neighbours` now wrapping, `Heading` reading a wrap backwards turns into a regression for the zoomed crop read-ahead. On a `Next` from the last file to the first, `Heading::to` sees the index fall and sets `Back`. `neighbours(files, 0, Back)` now returns `[last, 1]`, so `prefetch_crop` takes `last`, the file just left, as "the next neighbour". It spends the one crop read on a crop that `Zoom::page` has just released, and the following `Next` (to file 1) misses its crop. `Previous` from the first file to the last is the mirror case (`Forward`, `[first, len-2]`). Before this change, `neighbours(0, Back)` was `[1]` and `neighbours(len-1, Forward)` was `[len-2]`, so both wraps read the correct crop ahead. The ring itself only loses its ordering here (the left file is held through `keep`, as learnings.md says), but the learnings bullet "No miss follows from it" does not hold for `prefetch_crop`, which uses only the first neighbour. The app.md text "the first of `prefetch::neighbours` in the `heading` direction" is also now wrong at the wrap. Suggested fix: take the paging direction from the pager's `Move` where it is known (`Next`/`NextClamped` → `Forward`, `Previous` → `Back`), or make `Heading::to` aware of the wrap (pass `len`, and treat `last == len - 1 && index == 0` as `Forward` and the reverse as `Back` when `len > 2`). Add a unit test that pins the wrap's direction, and correct the learnings.md bullet.

### Fixed

1. `Heading::to` now takes the list length and keeps the paging direction across a wrap (more than two files), with a unit test; learnings.md and app.md updated.
