### Findings

1. **crates/native/src/main.rs:577 / 802-808 (`open`, `list`)**: the listing's background task holds the `opens` mutex across `watch::set`, which drops the previous `notify` watcher and opens a new `ReadDirectoryChangesW` handle on the folder, while `open` takes the same mutex on the UI thread to bump the counter (and `self.opens()` also locks it in every `update` closure: `list`, the reveal steps, the listing's result). A second click in the tree while the first open's watcher is being set therefore blocks the UI thread until that call returns. Now that the tree can open any folder, including one on a slow or unreachable UNC share or removable drive, that can mean a frozen window for seconds. The UI thread does not need this lock for correctness. Make the counter an `Arc<AtomicU64>` that `open` bumps without locking, and keep a separate `Arc<Mutex<()>>` that only the background tasks take around "check the counter == token, then `watch::set`". If A checks first, B's set runs after A's. If B sets first, A sees a moved counter and skips. So a later open's watcher is still never replaced, and the UI thread never waits on a watcher. Update the `opens` field comment and the `native-app.md` rule ("sets the folder watcher under the counter's lock") to match.
2. **docs/plans/20261113-gpui-tree-trash/plan.md:293**: Step 2's Done-when still says "(the `listing` counter is the folder token)". The implementation deliberately uses a new `opens` counter instead, because `listing` is bumped by every watcher re-listing and would cut a reveal short (the reason is recorded in `learnings.md`). The plan-guide asks for plan.md to be updated when the design changes, so reword that clause to name `opens` and give the reason. Otherwise Step 4, which reuses this token for the tree keyboard, will start from the wrong counter.
