## Round 1

**Reviewed commit**: `616f55eea633a3a0d652902ff427d83a3f709d66` feat(native): add the folder tree pane and open folders from it

STATUS: NEEDS_FIX

### Findings

1. **crates/native/src/main.rs:577 / 802-808 (`open`, `list`)**: the listing's background task holds the `opens` mutex across `watch::set`, which drops the previous `notify` watcher and opens a new `ReadDirectoryChangesW` handle on the folder, while `open` takes the same mutex on the UI thread to bump the counter (and `self.opens()` also locks it in every `update` closure: `list`, the reveal steps, the listing's result). A second click in the tree while the first open's watcher is being set therefore blocks the UI thread until that call returns. Now that the tree can open any folder, including one on a slow or unreachable UNC share or removable drive, that can mean a frozen window for seconds. The UI thread does not need this lock for correctness. Make the counter an `Arc<AtomicU64>` that `open` bumps without locking, and keep a separate `Arc<Mutex<()>>` that only the background tasks take around "check the counter == token, then `watch::set`". If A checks first, B's set runs after A's. If B sets first, A sees a moved counter and skips. So a later open's watcher is still never replaced, and the UI thread never waits on a watcher. Update the `opens` field comment and the `native-app.md` rule ("sets the folder watcher under the counter's lock") to match.
2. **docs/plans/20261113-gpui-tree-trash/plan.md:293**: Step 2's Done-when still says "(the `listing` counter is the folder token)". The implementation deliberately uses a new `opens` counter instead, because `listing` is bumped by every watcher re-listing and would cut a reveal short (the reason is recorded in `learnings.md`). The plan-guide asks for plan.md to be updated when the design changes, so reword that clause to name `opens` and give the reason. Otherwise Step 4, which reuses this token for the tree keyboard, will start from the wrong counter.

## Round 2

**Reviewed commit**: `2bf7057130e1da74a1971b24d195b9ff73b09470` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 2 / dismissal accepted 0 / re-raised 0

### Findings

1. **crates/native/src/main.rs:785-805 (`list`)**: `list` hands the previous scan (`self.scan.take()`) and the launch's eviction (`self.eviction.take()`) to the first listing that runs, and only that listing's background task waits for them. Before this branch a second listing could not overlap the first: the only open was the launch, and a re-listing waits on `Resync` until the scan is over. Now the tree can open folder B while folder A's listing is still in `previous.stop()` or `eviction.join()`. B's listing gets `previous = None` and `eviction = None`, so it goes straight on to `watch::set`, `scan::list` and `Scan::prepare` (the reconcile), and its `opened` starts pass 1 while the old scan may still be running and the 30-day eviction may still be deleting rows. That eviction can be deleting B's own folder rows while B's reconcile inserts them. This breaks the invariant in `list`'s doc comment ("reconcile it once the previous scan and the launch's eviction are over"), and with a launch that has no folder argument, two quick clicks in the tree during the startup eviction are enough to hit it. Make every listing wait on whatever an earlier listing is still waiting on. For example, keep a shared `Arc<Mutex<()>>` "settling" lock that each listing's background task holds across `previous.stop()` and `eviction.join()`, and take that lock in the UI thread's `list` call order. A simple way to get that ordering is to chain the waits: store the previous listing's "settled" signal (e.g. a `futures::channel::oneshot::Receiver` or a `Shared` future) on `Riffle`, and have each new listing await it before its own stop and join, then signal its own. Then B never reconciles or scans until A's stop and the eviction have finished. Add a note to `native-app.md`'s open rule as well.

### Fixes

1. Each listing now chains on the previous listing's `settled` oneshot (kept on `Riffle`) before stopping the previous scan and joining the eviction, then signals its own. Documented in `docs/agents/native-app.md`.
