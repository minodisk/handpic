Any Riffle-named NSIS release cut between Step 1 and Step 2 would therefore run its own uninstaller from `NSIS_HOOK_PREINSTALL` on every update. Then confirm with a compile under the name Riffle that the hook's code is absent, for example with a `!warning` probe inside the guarded branch.

2. **[crates/app/src/migrate.rs:103]**: The "next launch resumes" path can permanently discard the file that failed to move. After a failed pair, `main()` still starts the app (`crates/app/src/main.rs:661-666`), so `setup` and the plugins create fresh files in the new folder, such as an empty `index.sqlite`, `settings.json` or the `EBWebView` files. On the next launch the source is now the only real copy, but `move_file` sees the destination exists and runs `fs::remove_file(source)`, reports success, and `remove_dir_all` removes the old folder. Any transient failure on `index.sqlite` or `settings.json` (a lock, a permissions problem, a failed cross-volume copy) thus loses the user's index or settings silently, and the `invariant:` line appears only on the first launch. This goes beyond decision 9, which accepted the loss only for "Handpic having run before the Riffle update". It also falsifies the `copy_then_delete` comment that a later launch can trust `dest`, and Step 5's read-only resume check would pass while the data is gone. SQLite adds a second hazard: if `index.sqlite-wal` moved but `index.sqlite` did not, the moved WAL sits next to a new empty database. Fix: distinguish a resumed migration from the decision-9 case. For example, write a marker in the new folder before moving and clear it only when the pair completes, and while the marker is present let a remaining source replace the destination. Alternatively, do not launch on a failed pair (show an error and exit, before anything is created in the new folders). Add a test that fails a move, creates the destination as the app would, reruns, and asserts the source's content survives.

3. **[docs/agents/app-log.md:148]**: The new `data migration` row gives the details as `pair=<old>→<new> <path>: <error>`, but on macOS `remove_macos_leftovers` reports `<path>: <error>` with no `pair=` (`crates/app/src/migrate.rs:143`), under the same `invariant: data migration:` prefix. ## Round 2

**Reviewed commit**: `36c5d8bc231cbd4aca5845f8aca630bf35c25a73` fix: address local review round 1 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 2 / dismissal accepted 0 / re-raised 1

### Findings

1. **[crates/app/src/migrate.rs:149]**: (repeat of Round 1 item 2, SQLite part) A resumed run replaces `index.sqlite` but leaves the `index.sqlite-wal` and `-shm` that the app created next to the fresh database. The index runs in WAL mode (`crates/app/src/index.rs:640`) and nothing closes the connection on exit (the `RunEvent::ExitRequested` handler at `crates/app/src/main.rs:911` only flushes the sidecar writer, and it says `Drop` is not guaranteed during teardown), so the WAL normally survives the session. If the old folder has no `index.sqlite-wal` to overwrite it, the next open replays the empty session's frames over the restored database. SQLite validates a WAL by its own checksums, not against the database file, so this overwrites restored pages, including the schema page. The reverse order is lossy too: if `index.sqlite` fails but its `-wal` moves, which `move_tree` allows because it continues after a failure, SQLite discards the WAL when it creates the empty database, and the uncheckpointed frames are lost. Fix: treat the database and its `-wal` / `-shm` as one unit. On a replacing move, delete the destination's companions first, and do not move a `-wal` / `-shm` whose main file failed. Add a test that resumes with a marker, a destination `index.sqlite-wal` and no source WAL, and asserts that the stale WAL is gone.

2. **[crates/app/src/migrate.rs:171]**: (repeat of Round 1 item 2, new gap from the marker fix) The marker treats every remaining source as "the only real copy", which is false when `copy_then_delete` fails at its last step. There, `dest` is already the complete file and only `fs::remove_file(source)` failed, for example because a scanner holds the file without delete sharing. That is the scenario of the Windows test `a_source_that_cannot_be_removed_is_reported_and_nothing_is_deleted`. The app then runs on the real `dest` for a whole session, and the next launch sees the marker and replaces `dest` with the stale source, silently discarding that session's index and settings changes. The test does not catch this because nothing changes `dest` between its two runs. Fix: make the resume decision per file, so a source whose copy already landed is discarded rather than restored (for example, record such files in the marker), or adopt item 3's fix. Add a test that changes `dest` between the runs and asserts the change survives.

3. **[crates/app/src/main.rs:661]**: The migration runs before `tauri_plugin_single_instance`, so with the marker present a second launch replaces files under the running first instance. After a failed pair, double-clicking the app while it is open makes the second process call `migrate::run` with `resuming` true before it exits. On Linux and macOS the rename over the open `index.sqlite` succeeds, so the running app keeps writing to an unlinked inode and its session is lost; on any OS an unlocked `settings.json` is swapped under it. This also makes the `learnings.md` deferred item ("Neither can lose a file") wrong now that replacement exists. Fix: hold an exclusive lock for the migration and skip replacing when another process holds it or the app is running. Alternatively, take the other option from Round 1 item 2: do not start the app after a failed pair (show the error and exit before anything is created in the new folders), which removes the app-created files that items 1, 2 and 3 all depend on. Update the `learnings.md` line either way.

2. **[docs/plans/20261109-rename-to-handpic/plan.md:138]**: Stopping on a failed pair invalidates the plan, which this branch does not update. Line 92 (a failure logged by `setup`) and line 90 (the app carrying on and resuming) describe the same superseded behavior, and the plan's risk about the migration running before the logger needs the same update. Fix: record the "do not start after a failed pair" decision in the plan and change Step 5 to expect the error dialog and exit, then a clean relaunch with the old folder gone.

3. **[docs/plans/20261109-rename-to-handpic/learnings.md:66]**: "A WAL then always ends up next to the database it came from" is false in the decision-9 case. If `new/index.sqlite` already exists and has no `-wal`, `move_file` (`crates/app/src/migrate.rs:147`) discards the old `index.sqlite` but moves the old `index.sqlite-wal` next to the other database, and SQLite then replays those frames over it because it validates a WAL only against its own header and checksums. Decision 9 accepted losing the old file, not corrupting the kept database. Discarding a companion whenever the destination's main file exists is not a safe fix, because a resumed run can have `index.sqlite` landed with its source undeletable and its WAL still unmoved. A correct fix moves `-wal` / `-shm` before their main file, so that a destination main file with a remaining source companion can only mean a foreign database, and then discards that companion. The scenario is rare, so if that ordering is judged not worth the code, correct the sentence and record this as an accepted risk under decision 9.
