## Round 1

**Reviewed commit**: `9b087c4818a62cf9f48ba1cfc39173f5109a154f` feat(native): switch the sidecar format live from the Sidecar tab

STATUS: NEEDS_FIX

### Findings

1. **[crates/native/src/main.rs:991-1013]**: Two switches made back to back can persist the wrong format. `switch_format` sets `self.settings.format` on the main thread *outside* the `format_switch` lock and captures `format` by value into each background task, and the tasks then contend for a `std::sync::Mutex`, which does not guarantee FIFO order. Take Xmp -> Dop -> Both clicked within one drain (`DRAIN_TIMEOUT` can be seconds). If the second task gets the lock first, it writes `sidecarFormat = "both"`, and then the first task writes `"dop"`. `Writes` applies them in that order, so the store ends on `dop` while `settings.format` (and the radio) say `Both`. The next launch then silently uses `.dop` only. The Tauri path avoids this because `switch_sidecar_format` re-checks the current format *inside* `AppSwitchLock` (its doc comment says so: "the second one is a no-op when it already matches"), and the state write happens under that lock. Suggested fix: share the latest requested format with the tasks (e.g. an `Arc<Mutex<SidecarFormat>>`, or an `Arc<AtomicU8>` written on the main thread). Under the lock, either skip a task whose `format` is no longer the latest, or persist the latest value read under the lock instead of the captured one. Add a test of that rule if it can be pulled out as a pure function, and update the `native-app.md` section, which currently claims parity with `AppSwitchLock`.
