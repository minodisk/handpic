## Round 1

**Reviewed commit**: `6c5e804404a80a5710bdee3f5378c02f592edc61` feat(native): fill the Face focus, Eyes and Output filter sections

STATUS: NEEDS_FIX

### Findings

1. **crates/native/src/main.rs:911-916, 968-990 (with 917-921, 945-955)**: The race the implementer flagged is real. `Scan::start` (scan.rs:347-349) sends `Event::Done` and starts `run_faces_pass` right away on the same thread, so pass 2 writes rows and sends `FacesProgress` while `read_entries` is still out. Here is the sequence. (a) `Done` spawns `entries_of` on a background thread, and it reads the index at time t0. (b) Pass 2 writes file X after t0 and sends `FacesProgress { ready: [X] }`. (c) The main thread handles that event before the read's `this.update` closure runs, and `apply_face_ready` patches X's focus in `self.facts`. (d) The closure then calls `set_entries`, which replaces `self.facts` whole with the t0 snapshot, where X has no `eye_focus` and is `Unknown`. X's pass-2 values are gone for the rest of the session: nothing else re-reads the facts (`FacesDone` reads nothing, and `read_focus` only refreshes the overlay's `Focus`). On a fresh index under `candidates: ["good"]` or `eyes: [...]`, X stays filtered out (or stays in) wrongly until the next re-listing. Pass 2 runs on several worker threads and `entries_of` over a large folder is not instant, so the window is not theoretical. Fix: keep the `FaceReady` items received since the current `read_entries` was spawned (e.g. a `Vec<FaceReady>` on `Riffle` cleared in `read_entries` and in `opened`, appended in the `FacesProgress` arm), and in the closure call `filter::apply_face_ready(&mut this.facts, &pending)` right after `this.set_entries(entries)` and before the `refilter`. Re-applying is idempotent, so applying a value the snapshot already holds does no harm. Alternatively, merge in `set_entries` so the focus fields already set from pass 2 are not overwritten by a snapshot that lacks them. Add a unit test for the merge or reapply helper if it moves into `filter.rs`.
