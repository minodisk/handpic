## Round 1

**Reviewed commit**: `9ed6449ae5b0bfa7f8bde54e296dc9b37fa7b512` fix(engine): copy a shared .xmp on a date split and a file rename

STATUS: NEEDS_FIX

### Findings

1. **[crates/engine/src/rename.rs:178-186 (`shared_xmps`)]**: On a case-insensitive file system (Windows, macOS), mates whose stems differ only in case are not detected as sharing. `existing_sidecar` returns early with `wanted` spelled from each RAW's own stem whenever `wanted.exists()`. So for `a.ARW` and `A.NEF` next to one `a.xmp`, it gives `…\a.xmp` for the first and `…\A.xmp` for the second. Those are two different `PathBuf` keys (Path equality is case-sensitive), so each key has one RAW and `retain(len > 1)` drops both. The split then falls back to the old bug: `a.xmp` moves with whichever RAW goes first, and the other RAW loses it. `file_plan` has the same problem. The plan says this definition "covers the case-insensitive fallback", and the grouping by lower-cased name shows that was the intent, but the keying breaks it on the primary platform. Fix: inside each lower-cased-name group, key by the on-disk entry, not by `existing_sidecar`'s spelling. For example, canonicalize the returned path, or use the group's real directory entry found with `eq_ignore_ascii_case`, as the fallback does. Then use the same key for the `contains_key` lookup in `file_plan` and the `xmp_of` lookup in `split`. Add a test with mixed-case mates (`a.ARW`, `A.NEF`, `a.xmp`) that asserts both date folders get the `.xmp`.

### Fixed

1. `shared_xmps` now buckets the RAWs of a name group by the canonicalized sidecar path (key = first RAW's spelling), and `file_plan` checks membership by RAW instead of by the sidecar spelling. Added `mates_whose_stems_differ_in_case_each_get_the_shared_xmp` (case-insensitive file systems only).

### Findings

Callers depend on this. `file_plan` now has to look up by RAW membership, not by `contains_key(&sidecar)`, for exactly this reason. Update the comment to state the on-disk-entry rule and that the key is one member's spelling, so membership must be checked by RAW.

## Round 3

**Reviewed commit**: `7d64b42de88ec615e432ee4a5c3a7a8e232b2124` fix: address local review round 2 findings

STATUS: NEEDS_FIX

**Previous feedback**: addressed 1 / dismissal accepted 0 / re-raised 0

### Findings

1. **[crates/engine/src/datefolder.rs:316 (`split`, the `placed.contains(to)` check)]**: On a case-insensitive file system, mates whose stems differ only in case and that go to the **same** date folder fail to split. Take `a.ARW` and `A.NEF` sharing `a.xmp`, both dated 2026-10-31. `a.ARW` goes first: `A.NEF` is still in `dir`, so the `.xmp` is copied to `2026-10-31\a.xmp` and `placed` gets that path. Then `A.NEF` builds `to` = `2026-10-31\A.xmp`. That is a different `PathBuf`, so `placed.contains(to)` is false, and because no mate stays, `op` is `Some(Op::Move)`. `move_plan` then sees `A.xmp` already present (it is the same entry as `a.xmp`) and refuses with "A.xmp already exists". The result: `A.NEF` is listed as a failure and stays behind with the original `a.xmp`, and the folder is not removed. Before this PR, `A.NEF` would at least have moved. This is the case-differing-stem case Round 1 set out to cover; the Round 1 test only checks mates of different dates. Fix: match the placed copy by entry on disk, not by spelling. For example, use `placed.iter().any(|p| same_entry(p, to))` (make `rename::same_entry` `pub(crate)`), or key `placed` by `std::fs::canonicalize` of the copy once it exists. Extend `mates_whose_stems_differ_in_case_each_get_the_shared_xmp`, or add a sibling test, with both mates in one date group. Assert that both move, the date folder holds one `.xmp`, and `dir` ends up empty.

### Fixed

1. `split` now matches an already placed `.xmp` by entry on disk (`rename::same_entry`, now `pub(crate)`) instead of by spelling. Added `mates_whose_stems_differ_in_case_split_into_one_date_folder` covering both mates in one date group.
