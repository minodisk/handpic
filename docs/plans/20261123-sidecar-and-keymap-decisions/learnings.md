## Step 1: `.dop` flag across virtual copies

- `locate` now collects every depth-3 `{` line inside `Items`; the first is `Items[0]` (the `Doc` fields as before) and the rest are `VirtualCopy`s holding only their close, `ShouldProcess` and `ModificationDate`. Naming the struct `Copy` would have shadowed the `Copy` trait, hence `VirtualCopy`.
- The two-item test text is built from `_DSC0003.ARW.dop`: the item is the slice between `Items = {\n` and the last `}\n,\nUuid = "`, and the copy gets its own Uuid, `ModificationDate`, `Rating`, `Orientation` and a `ColorLabel`, so a byte-for-byte comparison shows which item a write touched.
- `mise run ci:local` failed twice on `scan::tests::a_cancel_ends_a_scan_waiting_on_a_pause_or_a_permit` (`crates/core/src/scan.rs`, untouched here): `took 1.14s` / `took 1.10s` against its 1 s bound under the whole core suite's load. It passed alone in 0.57 s and on the third full run.
- `CLAUDE.md`'s `src/dop.rs` clause ("rating, the tri-state pick / reject flag as `ShouldProcess`, and `ColorLabel`") still holds and was left unchanged.

## Step 2: skip oversize sidecars in `Rewrite Sidecars from Index…`

- `targets` now takes the format and lists with `read_listing(dir, Some(format))`, then drops a row whose RAW has a sidecar of the format's kinds (`trash::sidecars_of`) with `size > MAX_SIDECAR_BYTES`, the same comparison `sidecar::reconcile_of` makes. The filter runs after the "no row" refusal and before `mark_dirty`, so a folder whose every row is oversize still opens the dialog on a rewrite of 0 files.
- `Summary` gained `skipped`, the same figure as `Preview::skipped` (taken from the same `targets` call). Neither struct reaches MCP clients as is: `companion.rs` shows only the dialog's text, so the new field changes no tool reply.
- The dialog's row now reads `N files skipped (no judgment on record, or a sidecar larger than 4 MiB)`, the MiB figure taken from `MAX_SIDECAR_BYTES`; the status line adds `, N skipped` before `, N failed`.
- `CLAUDE.md`'s `src/foldersidecars.rs` clause still holds and was left unchanged.
- The first `mise run ci:local` failed on the exactly-`MAX_SIDECAR_BYTES` test: a 4 MiB file of filler is not skipped, so the writer patches it and fails with `no rdf:Description element`. The test now pads a real XMP packet with whitespace before `<?xpacket end` to exactly 4 MiB, which the writer patches.

## Step 3: copy a shared `.xmp` on a date split and a file rename

- `FilePlan` is now `steps: Vec<(Op, from, to)>` with `Op::Move` / `Op::Copy`, and `file_run` takes an `apply(op, from, to)` closure and a `remove(path)` closure, so the tests inject failures into copies and into the delete of a copy as they did into renames. `rename::apply` is the real one: `std::fs::rename`, or a copy through `File::create_new` (never overwriting, the partial target removed on a failed write).
- "Shares" is `rename::shared_xmps(dir)`: one `read_dir`, the RAWs grouped by the lower-cased `.xmp` name they would mint, and `existing_sidecar` called only inside groups of two or more, so a folder without shared stems costs no extra `existing_sidecar` fallback `read_dir`s. Inside a group the RAWs are bucketed by the canonicalized sidecar path, so mates whose stems differ only in case still share one `.xmp` on a case-insensitive file system.
- The split's rule, decided at each file's turn in `split` (so a failure is already known): a shared `.xmp` is copied while another of its RAWs is still in the source folder (undated, failed or not moved yet), moved with the last one, left out when the date folder already holds it (a same-date mate placed it), and removed from the source once the last mate moved into a folder that already held it. So a mate whose move fails always keeps the original, and a folder whose every file moved is still removed. Choosing only from "a mate is still in the folder" without the `placed` set would refuse the second same-date mate's move as "a.xmp already exists".
- `file_plan` plans nothing for a shared `.xmp` whose copy target is the shared file itself (a case-only rename or a rename to another RAW extension of the same stem).
- `split_folder`'s index rows follow by `Index::move_file` as before; the new test sets a rating on both mates and finds each in its date folder's `rows_of` after the split.
- The heading of the `docs/agents/photolab.md` section lost "or a shared sidecar", since a rename now leaves the shared sidecar with the RAW that stays; no link pointed at its anchor. `CLAUDE.md`'s `src/rename.rs` and `src/datefolder.rs` clauses still hold and were left unchanged.
- A bash heredoc holding a Python script with `'''` strings and Rust closures failed with "unexpected EOF while looking for matching `'`"; the same edits went through the Edit tool instead.
- `mise run ci:local` was killed by Claude Code for low system memory while the engine tests ran (none had failed). By the user's decision it was not re-run: the step was committed after `mise run fmt`, the targeted `rename::` / `datefolder::` tests and clippy on `handpic-engine`, and CI is left to the PR's GitHub checks.

## Step 4: a stored shortcut override wins over an un-overridden default

- The yield is one pass in `from_overrides` right after `pending` is built: every action with no entry in `pending` (no stored override, or an invalid or forbidden one) loses each key some pending override asks for, logged at `warn` as `moving "d" from performance to next: a stored shortcut binds it`. The log names the first pending override in action order that wants the key, which is the one the retries give it to when two want it. After the pass, a default's key is held only by its own overridden action or by nobody, so the existing retry loops and the `partial` recompute run unchanged and resolve only override-against-override conflicts.
- `overrides()` now skips an action with no keys; the reload derives the empty action again, so `from_overrides(Some(&keymap.overrides())) == keymap` holds for every new test.
- The tests that built an inactive override from a default's key (`{"reject": ["arrowup"]}`) now use two overrides wanting one key (`{"reject": ["r"], "clear": ["r"]}`), where `clear`, later in action order, is the inactive one. `ctrl_alt_keys_are_bindable` also changed: `{"reject": ["ctrl+alt+1"]}` now takes the key from `red`. A new `an_unusable_override_displaces_no_default` pins that a forbidden or invalid override takes nothing.
- The `crates/app` test (`context::tests::an_action_a_stored_override_left_without_keys_binds_and_shows_none`) loads `{"reject": ["p"]}` and checks `Bindings` (no `x`, `p` to reject), the Judgment group's `shortcut_rows` (a `pick` row with no keys) and `shortcut_of` (empty). `settingsview.rs`'s row was read, not changed: with no keys it draws no `Kbd` and keeps `+`.
- `CLAUDE.md`'s `src/shortcuts.rs` clause still holds and was left unchanged.
- Local checks: `mise run fmt`, the 52 `shortcuts::` engine tests and `cargo clippy -p handpic-engine --all-targets -- -D warnings` passed. The targeted `crates/app` test run (`cargo test -j 2 --bin handpic -- context::tests::an_action_a_stored_override`) was killed by Claude Code for low system memory while it compiled GPUI, so the new app test has not run locally; `mise run ci:local`, which builds the same crate, was not tried after that. By the user's decision CI is left to the PR's GitHub checks.
- A bash heredoc holding a Python script with `'''` strings again failed ("unexpected EOF while looking for matching `'`") before running anything; the edits went through the Edit tool.
